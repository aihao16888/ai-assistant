## 一、本轮要验证什么

本轮不是确定三个长期栏目，也不是提前决定首篇内容，而是用三种发现路径，从小红书真实讨论中找到值得研究的 AI 应用任务。

**搜索的对象不是“AI 有什么能力”，而是“用户想完成什么事情、AI 在其中能帮上哪一步、最后能交付什么结果”。**

三条发现路径：

1. **需求发现：** 用户想让 AI 帮自己做什么？
2. **实践发现：** 别人已经用 AI 完成了什么具体任务？
3. **问题发现：** 用户在使用 AI 时遇到什么失败、限制或不满意？

它们是搜索入口，不是账号的三个内容栏目，也不代表未来内容比例。一个具体任务可能同时出现在两条或三条路径中。

## 二、三条发现路径与首轮搜索种子

以下 12 个词是第一轮搜索起点，不是最终选题。搜索结果不相关时应改写，不为了完成数量而保留低质量结果。

### A. 需求发现：用户想让 AI 帮忙完成什么？

| ID | 首轮搜索词 | 想发现的信号 |
|---|---|---|
| A1 | 有没有 AI 能帮我完成日常重复工作 | 用户希望减少哪些重复操作 |
| A2 | 怎么用 AI 从大量资料中找到指定信息 | 用户需要定位、筛选、核对哪类信息 |
| A3 | 如何让 AI 根据要求处理文件并输出结果 | 用户希望输入什么材料、得到什么交付物 |
| A4 | 有没有 AI 可以替我完成多个步骤的任务 | 用户希望把哪些连续步骤交给 AI |

### B. 实践发现：别人已经用 AI 做成了什么？

| ID | 首轮搜索词 | 想发现的信号 |
|---|---|---|
| B1 | 我用 AI 完成了一项以前需要人工做的工作 | 真实任务、操作过程和结果 |
| B2 | AI Agent 真实任务执行全过程 | Agent 实际承担了什么任务、交付了什么 |
| B3 | 普通人用 AI 完成实际任务的经验 | 非开发者可借鉴的使用方式 |
| B4 | 用 AI 把多个软件之间的工作串起来 | 跨应用任务、数据流转和自动化场景 |

### C. 问题发现：AI 使用中有什么没有解决好？

| ID | 首轮搜索词 | 想发现的信号 |
|---|---|---|
| C1 | AI 处理文件经常出错怎么办 | 文件解析、内容遗漏、格式和数据错误 |
| C2 | AI 执行复杂任务为什么会失败 | 中断、漏步骤、错误操作和人工接管 |
| C3 | AI 生成的结果怎样核实准确性 | 结果核验、原文依据和错误发现 |
| C4 | AI 工具实际使用有哪些限制和坑 | 费用、权限、隐私、兼容性和使用门槛 |

### 搜索词如何扩展

不要机械地把这 12 个词原样搜索完就结束。先看结果是否出现具体任务，再从结果中提取更自然、更精确的表达。

例如，如果搜索中发现用户经常讨论“从多份材料中找出缺失项”，可以继续搜索“AI 对照清单检查文件缺项”“AI 核对合同条款并标注原文”等更具体的任务表达。

这类表达只是说明如何扩展搜索，不代表我们已经选定文档核查、Excel、Agent 或任何其他应用作为主线。

## 三、首轮采集怎么控制范围

建议先按三条路径各选 2～3 个搜索词试搜，观察搜索结果质量；确认关键词能找到相关内容后，再补充其余搜索词。

- 每个搜索词先快速浏览一小批结果，优先判断是否包含具体任务、真实过程或明确问题。
- 对明显重复、纯工具宣传、只有概念介绍且没有用户任务的内容，不必深入拆解。
- 每条路径挑选少量代表性帖子深入阅读，重点看正文、操作证据和评论区。
- 不追求固定帖子数量。某条路径信号很弱，就记录“当前未发现足够信号”，而不是凑样本。
- 搜索结果排序、互动数据和可见范围受平台状态影响，不能把前几条结果当成整个用户群体的代表。

第一轮先以小红书为主，目的是了解中文用户如何表达需求、展示使用过程和提出问题。只有当具体候选任务出现后，再使用 Reddit、Hacker News、GitHub 和官方文档补充技术实践、方案和事实核验。

## 四、每条帖子要提取什么

不要只记录标题、点赞数和工具名称。围绕“任务—过程—交付”拆解：

| 维度 | 要回答的问题 |
|---|---|
| 用户与场景 | 谁在什么情况下需要做这件事？ |
| 原始任务 | 用户原本要完成什么？ |
| 原有做法 | 以前靠人工、公式、软件还是其他工具？ |
| AI 承担的步骤 | AI 实际做了哪一步？是否调用工具或脚本？ |
| 输入 | 用户提供了什么材料、数据或指令？ |
| 最终交付 | 最后得到的是文件、表格、报告、图片、视频，还是完成的操作？ |
| 实际效果 | 有无可见的前后对比、结果或验证？ |
| 人工介入 | 哪些步骤仍需要用户判断、确认或修正？ |
| 失败与限制 | 哪些情况会出错、不能完成或成本过高？ |
| 评论区信号 | 其他用户追问什么、质疑什么、希望增加什么？ |
| 我们的机会 | 能否用自己的测试、解释或更简单的方法补上缺口？ |

点赞、收藏和评论只作为采集时点的辅助信号。不能用高赞替代需求判断，也不能把作者声称的效果当成已经验证的事实。

## 五、怎样从素材形成候选选题

### 1. 按具体任务聚类，而不是按工具分类

不要把“ChatGPT”“Agent”“Python”“MCP”“Excel”分别当成选题类别。

应根据用户要完成的任务、输入材料、预期交付物和主要障碍聚类。同一种任务可能有多种实现方式；同一个工具也可能解决完全不同的问题。

### 2. 候选选题必须落到具体任务

每个候选至少能够说清：

- 用户在什么场景下遇到什么问题？
- 他希望 AI 帮忙完成哪一项具体任务？
- 输入是什么，预期交付物是什么？
- 现有办法有什么麻烦或不足？
- 我们能提供什么新的帮助或解释？
- 能否通过实际操作或可靠资料验证？

例如，“AI 自动化办公”太宽；“按指定条件核对两份表格，将匹配结果回填到模板，并把无法匹配的记录单独列出”才是可研究的任务描述。

这个例子只用于说明选题需要具体到任务和交付物，不代表 Excel 是本轮既定主线或优先选题。

### 3. 不预设必须使用 Agent、Python 或某个工具

先定义任务，再比较合适的实现方式。可能的方式包括：

- 直接使用模型的文件理解和数据分析能力；
- 使用 Excel 公式、筛选、Power Query 等现有功能；
- 使用 Python 脚本处理文件和数据；
- 使用 Office API 或其他软件接口；
- 由 Agent 组织模型、脚本和外部工具，完成多步骤流程。

是否使用 Agent，取决于任务是否需要跨步骤规划、工具调用、状态管理或人工确认。是否使用 Python，取决于文件格式、数据规模、处理规则、可重复性和输出要求。不能为了展示 AI 而强行选择更复杂的方案。

### 4. 候选选题筛选

不做机械总分。重点判断：

1. 用户任务是否具体，最终结果是否明确？
2. 对普通用户是否有实际帮助？
3. 现有内容是否已经充分解决，还是仍有真实缺口？
4. 我们是否能获得可靠资料或亲自复现？
5. 是否能把核心价值压缩成一篇简短的小红书笔记？
6. 隐私、版权、费用和平台风险是否可控？

通过判断后再进入候选选题池。未验证的想法标记为假设，不写成已完成的成功案例。

## 六、研究可以深入，发布内容必须短而清楚

我们不是写技术博客。内部研究可以充分，但公开笔记不需要复述整套研究过程，也不需要讲完整技术架构。

一篇笔记优先只解决一个具体问题，展示一个有用方法或结果。可以按题材选择不同讲法，例如：

- 展示一个原本麻烦的任务，以及 AI 实际帮上了哪一步；
- 展示输入和输出，让读者看见结果差异；
- 展示一个容易失败的环节，以及怎样避免；
- 用一个具体例子解释一个技术概念；
- 分享一个简单可复现的方法或提示。

不规定统一字数、图片数量、标题公式或固定叙事模板。不要把内部研究报告改写成长篇笔记，也不要为了短而删掉关键条件、证据和风险。

## 七、首轮交付物

完成首轮探索后，应该得到：

1. 三条发现路径的搜索记录和实际查询词；
2. 一批有来源链接的代表性帖子及评论信号；
3. 按用户任务聚类后的需求清单；
4. 少量具体的候选选题，每个都写明输入、任务和最终交付物；
5. 对每个候选的价值、内容缺口、验证方式和风险的初步判断；
6. 推荐进入下一步研究的 2～3 个候选，并说明为什么。

这里的“2～3 个”是供下一阶段比较的工作建议，不是必须凑齐的数量。如果实际只有一个选题值得研究，就只保留一个；如果暂时没有合适选题，就继续发现信号，不要硬选。

## 八、执行边界与当前状态

- 本文件是首轮搜索计划，不代表搜索已经执行。
- OpenCLI 只用于必要的只读搜索、笔记和评论读取，不自动点赞、收藏、关注、评论、私信或发布。
- 不保存 Cookie、Token、验证码、私信或无关个人信息。
- 不把第三方作者的体验、图片、视频和结论写成自己的。
- 采集结果要记录时间、来源和样本局限。
- 仅在 `test` 分支更新；未经用户明确授权，不合并到 `main`。

当前状态：搜索路径和 12 个首轮搜索种子已定义；尚未在用户本机运行 OpenCLI，也尚未取得新一轮小红书帖子和评论数据。
