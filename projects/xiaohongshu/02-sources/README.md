## 一、为什么要采集外部素材

外部素材不是为了收集一堆热门帖子，也不是为了模仿别人写笔记。

我们希望通过外部资料回答：

- 用户正在讨论哪些真实问题？
- 用户如何描述自己的困难和期待？
- 哪些问题在不同帖子、不同作者或不同平台反复出现？
- 现有内容已经解释了什么，还有什么没有讲清楚？
- 某项 AI 能力是否真的存在，产品有哪些限制？
- 有没有可复现的方案、真实案例或失败记录？

**采集是发现信号；拆解是理解信号；选题是作出判断。三者不能混为一谈。**

## 二、外部来源及其用途

| 来源 | 主要用途 | 使用方式 |
|---|---|---|
| 小红书 | 中文用户需求、搜索表达、笔记形式、评论区问题 | 搜索相关帖子，深入阅读代表性笔记和评论 |
| Reddit | 技术用户的使用体验、问题、争议和替代方案 | 按具体问题或工具检索，不把社区声音当成国内用户画像 |
| Hacker News | 新技术、产品实践、开发者讨论和反例 | 关注讨论中的具体经验、链接和争议 |
| 官方文档/更新日志 | 核实产品能力、版本、限制、费用和规则 | 优先使用官方来源，记录查阅日期 |
| GitHub 项目/Issue | 复现方案、实现细节、已知问题和维护情况 | 查看 README、示例、Issue 和最近更新 |
| 自己的实践 | 一手体验、操作过程、结果和失败 | 独立记录，不用外部作者的体验代替自己 |

不同来源回答不同问题。小红书热度不能证明技术正确；官方文档不能证明用户一定觉得好用；单个用户体验也不能代表所有用户。

## 三、使用 OpenCLI 采集小红书

OpenCLI 提供小红书等站点的命令适配器，也提供读取笔记和评论等能力。具体命令随安装版本和适配器更新，**每次采集前先查看本机命令帮助，不把仓库文档或网络示例当成永远不变的接口**。

### 1. 先检查环境与命令

~~~bash
opencli doctor
opencli list
opencli xiaohongshu search --help
opencli xiaohongshu note --help
opencli xiaohongshu comments --help
~~~

如果命令名称、参数或输出格式与本文示例不一致，以本机帮助信息和当前安装版本为准。

小红书搜索、笔记和评论读取通常依赖浏览器登录状态。需要登录时，由账号持有人在浏览器中正常登录；不要把 Cookie、登录态、验证码或账号凭证写入仓库或发送给其他人。

### 2. 只读采集示例

以下命令用于说明工作方式，执行前先确认本机帮助信息：

~~~bash
# 搜索用户问题或具体任务
opencli xiaohongshu search "AI 整理资料" --limit 10 -f json

# 读取某篇笔记（使用搜索结果返回的完整笔记 URL）
opencli xiaohongshu note "<完整笔记URL>" -f json

# 读取该笔记的评论
opencli xiaohongshu comments "<完整笔记URL>" -f json
~~~

建议先用一个关键词做小规模测试，确认返回结果、字段、链接和时间信息都合理，再扩大到同一主题的其他表达。

注意：
- 搜索结果可能受登录状态、站点页面、适配器版本和平台变化影响。
- 不要假设搜索结果已按最新、最热或特定内容类型排序；先核对当前适配器能力。
- 笔记详情 URL 可能包含 xsec_token 等访问参数。不要自行拼接或猜测参数；优先使用搜索结果返回的原始 URL。
- 如果出现登录墙、验证码、安全限制、异常空结果或访问受限，先停止并检查原因；不要循环重试、绕过验证或提高请求频率。
- 只使用搜索、笔记读取、评论读取等必要的只读命令。不要通过本工作流点赞、收藏、关注、评论、私信、发布或模拟真人互动。

### 3. 首轮采集范围

每次采集前先写一个具体研究问题，不要从“AI”这种过宽的关键词开始。

可以从以下几种词语表达出发：
- 用户问题：遇到什么困难？
- 用户任务：想让 AI 帮忙完成什么？
- 用户结果：希望得到什么结果？
- 技术能力：哪项 AI 能力值得理解？

初次探索可以从每个方向 2～3 个不同表达的查询词开始，每个查询先看约 5～10 条结果；合并重复笔记后，再深入阅读约 3～5 篇代表性内容。这只是控制首轮工作量的建议，不是采集配额。若已经看到重复需求、明显反例和主要争议，就不必为了凑数量继续采集；如果搜索结果偏题，再调整查询表达。

这是一种控制成本的研究方式，不是固定采集配额。

## 四、每条素材需要记录什么

建议为每条来源分配稳定的 Source ID，例如 XHS-20261127-001、REDDIT-20261127-001。

| 字段 | 说明 |
|---|---|
| source_id | 内部唯一编号 |
| platform | xiaohongshu / reddit / hackernews / github / official 等 |
| query | 本次使用的搜索词或发现入口 |
| url | 可公开访问的来源链接；清理临时访问参数 |
| title | 原标题 |
| creator | 公开昵称；仅在分析需要时记录 |
| published_at | 原文发布时间；未知就留空 |
| captured_at | 实际采集时间 |
| metrics_snapshot | 采集时可见的点赞、收藏、评论等数据 |
| content_summary | 自己概括的内容摘要，不复制整篇原文 |
| user_signals | 从帖子和评论中提取的问题、需求、疑问 |
| evidence_type | 用户经验 / 官方资料 / 技术实现 / 观点等 |
| limitations | 样本、数据、作者身份或信息完整性限制 |
| usage_note | 为什么保存、后续可能用于什么研究 |

### 记录数据时的注意事项

- 互动数据是某个时间点的快照，不是永久值；必须同时记录 captured_at。
- 不同平台的点赞、收藏、浏览定义不一定相同，不要直接横向比较。
- 缺失字段就标记“未取得”，不要推算或补造。
- 作者粉丝量、发布时间等信息只有在可见且确实有分析价值时才记录。
- 一条来源可以支持多个需求信号；一个需求信号也可以关联多个来源。
- 重要结论必须保留来源链接和必要的原文上下文。

## 五、怎样深入拆解一篇笔记

深入阅读时，不只是总结“作者讲了什么”，而要回答：

1. 这篇笔记面向谁？
2. 读者在什么场景下会需要它？
3. 它解决的是哪个具体问题？
4. 它向读者承诺了什么结果？
5. 作者展示了什么证据？
6. 评论区在追问、质疑或补充什么？
7. 哪些内容已经讲得很好？
8. 哪些问题仍然没有得到回答？
9. 我们是否有自己的证据和能力，提供更真实、更准确或更有帮助的回答？

拆解结果应当形成需求信号和内容缺口，不要把原作者的标题、结构、个人经历和数据直接搬到自己的选题里。

## 六、外部素材的使用边界

### 1. 不把帖子当作事实来源

- 用户分享的体验可以作为个体经验；
- 产品能力和技术结论要回到官方文档或可复现测试；
- 价格、版本和平台规则要检查日期；
- 对于互相矛盾的说法，记录分歧并继续核实。

### 2. 不把对标变成洗稿

可以学习问题选择、解释顺序、证据呈现和互动中暴露的用户需求；不能复制他人的完整文案、图片、视频、独特创意、个人经历和实测数据。

仓库中优先保存来源链接、自己的摘要和短小的必要引用，不为了“资料完整”而复制整篇内容。需要使用他人图片或视频时，先确认授权和合理使用边界。

### 3. 保护隐私与账号安全

- 不采集或保存与研究无关的个人信息；
- 评论区用户尽量以匿名方式记录，保留问题本身即可；
- 不把登录 Cookie、Token、验证码、私信或非公开信息提交到仓库；
- URL 中的临时访问参数应从提交内容中清理；需要重新访问时可通过正常搜索重新获取；
- 不使用自动互动或自动发布功能。

### 4. 遵守平台当期规则

OpenCLI 能够执行某项操作，不代表平台允许该操作，也不代表该操作适合账号运营。当前工作流只用于有限、必要的只读研究。发布 AI 生成或 AI 辅助内容时，按小红书当期规则检查声明要求；不制作虚假体验、不批量生成同质化内容、不用自动化冒充真人运营。

## 七、目录与文件约定

~~~text
02-sources/
├── README.md
└── xhs/
    ├── ai-agent/          # 已有 Agent 对标研究，作为历史专题素材保留
    └── ai-job/            # 已有 AI 求职素材，作为一个应用案例保留
~~~

后续只有当某个候选选题确实需要外部研究时，再为它建立专题子目录。不要先建立大量空目录。

原始来源和自己的研究结论分开保存：
- 原始来源：链接、采集时间、必要字段和短摘要；
- 需求信号：从来源中提取的用户问题；
- 研究结论：放在对应选题的研究文件中，并引用 Source ID；
- 自己的实测：放在案例记录中，不混入外部作者的体验。
