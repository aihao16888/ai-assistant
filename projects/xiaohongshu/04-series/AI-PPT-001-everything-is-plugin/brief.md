## 1. 真实任务

需要给同事做一次 DeepSeek Harness 技术分享。我们选择官方产品和代码仓库中的一个核心主题：

**Everything is a Plugin：DeepSeek Harness 的插件化架构与实现机制。**

这次分享不试图介绍整个 DeepSeek Harness，也不把 Agent Loop、MCP、Java 集成等主题分别展开。只有在解释插件化设计时确实需要，才引用相关机制作为背景。

本次要解决的问题是：

> 我们遇到一个还不熟悉的开源项目，怎样借助 AI Agent 阅读相关资料和源码，真正弄清楚它的插件化设计，并把理解整理成一份准确、清楚、可以用于内部分享的演示文稿？

## 2. 技术分享的目标

让听众在分享结束后能够解释：

1. DeepSeek Harness 中的 Everything is a Plugin 指什么，适用边界是什么；
2. 插件在运行架构中承担什么角色；
3. Cordis 如何通过 Context、Service、inject、生命周期、Event 和 Effect 等机制组织插件；
4. 插件如何注册能力、声明依赖、管理副作用并参与运行；
5. 多个插件如何被组合进 Harness 的运行环境；
6. 这种设计带来哪些好处、约束和需要留意的地方。

以上是待研究的问题，不是已经验证的结论。术语含义、调用顺序、具体 API 和架构关系必须回到固定版本的官方文档与源码核实。

## 3. 分享范围与边界

### 本次重点

- Everything is a Plugin 的设计含义和边界；
- Cordis 的插件抽象及 Context；
- Service 的提供与 inject 依赖声明；
- 插件生命周期和副作用清理；
- Event / Effect 等机制在插件协作中的作用；
- 选择一个真实内置插件，追踪它从加载、依赖到提供能力的过程；
- 必要时解释 Profile、Bundle、Patch 如何组合插件，但不展开成独立专题。

### 本次不做

- 不做 DeepSeek Harness 全仓库导览；
- 不把所有子系统都塞进一份 PPT；
- 不将 Cordis、Koishi 和 DeepSeek Harness 的关系讲成没有证据的设计因果；
- 不照抄官方文档 API 清单；
- 不为了展示 AI 能力而引入无关的 Agent、MCP 或 Java 案例。

## 5. PPT 制作路径：HTML 先行，Office 后续

### 阶段 A：HTML 幻灯片原型

先用 HTML 做第一版幻灯片，主要目的是快速验证：

- 技术叙事是否清楚；
- 页面顺序是否合理；
- 每页核心观点是否突出；
- 架构图、流程图是否准确且易懂；
- 整体视觉节奏是否适合现场讲解。

第一版优先做静态、可浏览、便于快速修改的幻灯片，不为炫技加入不必要的动画或交互。可以评估 reveal.js 等方案，但暂不在任务书中锁定技术框架。

HTML 对快速预览和迭代可能更方便，但不代表所有设计都比 PPTX 简单；还要检查浏览器、字体、图片路径、投屏和离线环境。

### 阶段 B：内容和视觉审核

HTML 原型完成后，先审核内容和视觉，不直接进入 Office 制作：

- 每页是否有明确结论；
- 技术关系和源码证据是否一致；
- 页面是否过密、重复或缺少必要解释；
- 讲解时长是否合适；
- 连续播放时是否能形成完整的分享过程。

### 阶段 C：原生可编辑 Office PPTX

HTML 原型通过审核后，再根据已确认的页面结构和视觉规范制作 Office PPTX。

优先使用原生文本、形状、表格和图表对象。不要简单把 HTML 每页截图后塞进 PPT，也不要默认复杂 HTML 可以无损转换为可编辑 PPTX。

对确实适合转换的元素，可以测试转换工具；转换后仍需逐页检查文字、图表、字体、对齐和编辑能力。

### 交付判断

- HTML：第一阶段的可播放原型，也可作为浏览器演示版本；
- PPTX：面向同事交接和后续修改的正式 Office 版本；
- PDF：如有分发需要，再从通过验收的正式版本导出。

如果实际场景最终只要求浏览器演示，可以重新评估是否需要 PPTX；在此之前，不提前省略 Office 验收。

## 6. 初步页面结构

以下只是用于启动研究的结构假设，不能代替源码研究后的最终大纲。预计 8～10 页、约 15～20 分钟，需根据听众和材料调整。

1. **问题引入：** 为什么 Harness 需要插件化组织运行能力？
2. **概念边界：** DeepSeek Harness 所说的 Everything is a Plugin 到底指什么？
3. **核心抽象：** Plugin、Context、Service 分别承担什么职责？
4. **依赖协作：** 插件怎样声明和使用其他插件提供的 Service？
5. **生命周期与清理：** 插件加载、运行、卸载和副作用管理如何工作？
6. **事件与上下文：** Event、Effect 等机制怎样支持插件协作？
7. **源码追踪案例：** 一个真实内置插件如何被加载、取得依赖并注册能力？
8. **运行组合：** 必要时说明 Profile、Bundle、Patch 怎样组合插件。
9. **设计价值与边界：** 插件化解决了什么问题，又引入什么复杂度？
10. **总结：** 用一张图回顾插件从加载到参与运行的完整过程。

若源码研究发现某些机制并不适合独立成页，可以合并；不为了凑页数保留内容。

## 7. 同步记录制作过程，但先完成 PPT 再制作系列笔记

本项目有两种成果，不能混为一谈：

### 成果 A：技术分享 PPT

面向公司技术同事，强调技术准确性、实现细节、架构关系、证据和专业表达。

### 成果 B：小红书系列笔记

面向普通 AI 用户和希望提高工作效率的人，强调具体问题、操作过程、结果、限制和可复用经验。表达要通俗，但不能为了通俗牺牲事实准确性。

两种成果共享同一真实任务和过程记录，但不是同一份内容的简单改写。

**执行顺序：**

- PPT 制作是主线，先完成并验收技术分享；
- 在每个制作阶段同步记录 AI Agent 的实际参与、输入、输出、失败、人工修正和耗时，避免事后凭记忆补写；
- PPT 完成后，再从过程记录中筛选有证据、有独立价值的笔记；
- 小红书笔记不需要按 PPT 页码逐页拆，也不需要强行把每个步骤都变成一篇。

## 8. 每个阶段都提取两层价值

每条候选笔记优先采用这样的思考顺序：

1. **具体经验：** 先展示我们在 DeepSeek Harness 的 Everything is a Plugin 研究和 PPT 制作中，实际遇到的问题、使用的操作、AI 的输出和验证结果；
2. **通用经验：** 再解释这个做法能否迁移到其他 PPT 任务，例如业绩汇报、项目汇报、培训课件或方案介绍；
3. **适用边界：** 说明哪些部分可以复用，哪些必须根据新场景重新处理。

例如：

- 具体经验：如何让 Agent 在一个大型 GitHub 仓库中缩小范围，追踪 Cordis 插件的真实实现；
- 通用经验：制作业绩汇报时，如何从多份材料中定位与本次汇报目标相关的数据和依据；
- 适用边界：源码依赖关系与业务指标口径不同，不能照搬技术分析结论，但“先明确问题、再限定资料范围、最后逐条核验依据”的研究方法可以迁移。

不是每篇笔记都必须硬套“DeepSeek 案例 + 通用经验”相同模板。根据具体内容选择讲法；只有经过实际验证的方法才上升为通用经验。

## 11. 验收标准

### 技术分享 PPT

- 分享主题始终聚焦 Everything is a Plugin；
- 重要结论有固定版本的官方文档或源码依据；
- 真实插件案例能从源码解释清楚；
- 术语和机制没有混淆；
- 页面顺序能形成完整讲解；
- HTML 在目标浏览器和投屏环境可正常播放；
- Office PPTX 中标题、文字、图形、表格和图表按要求可编辑；
- 完成一次真实试讲，并记录需要修改的内容。

### 小红书笔记

- 先讲本次实践中真实发生的具体问题和操作；
- 再提炼能迁移到其他 PPT 场景的经验；
- 普通用户能够理解，不堆砌技术术语；
- 不把技术分享内容直接压缩成笔记；
- 不编造成功率、效率提升和节省时间；
- 不要求 28 篇全部发布，不使用同一套机械模板。
