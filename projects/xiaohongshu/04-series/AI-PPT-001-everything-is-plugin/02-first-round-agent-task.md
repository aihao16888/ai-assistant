## 1. 任务目标

你不是来写一份官方文档摘要，也不是来开发一个插件。

你的任务是帮助研究者完成一次有证据的技术调查：

> 从不了解 DeepSeek Harness 的 Everything is a Plugin 开始，研究它的设计思想、运行机制和真实产品实现，最终让研究者能够独立解释、画图、回答问题并完成内部技术分享。

研究成果必须回答：
- 它到底是什么，边界在哪里；
- 为什么采用这样的设计；
- 它在运行时如何实现；
- 插件如何提供能力、声明依赖、协作、替换和卸载；
- 这种设计有什么价值、代价和适用边界。

**研究目标是获得可解释、可验证的知识，不是完成固定数量的文档阅读，也不是尽可能多地扫描代码。**

## 3. 研究方法

采用问题驱动的证据链，而不是按文件目录机械阅读：

1. 明确当前要回答的具体问题；
2. 从官方文档/API 参考找到概念和契约；
3. 从固定 Commit 源码定位真实实现；
4. 从对应测试检查边界行为和失败场景；
5. 只有文档、源码、测试仍无法回答时，才设计最小运行实验；
6. 用自己的语言解释结论；
7. 标明证据不能证明什么，保留仍然开放的问题。

资料范围可以扩展，但每次扩展都必须说明它回答了哪个问题。禁止为了“读完整个仓库”而扫描 26,160 个路径。

## 4. 必须避免的概念混淆

- Plugin 不等于 Service；
- Plugin 不等于 npm package；
- Cordis 配置项不等于插件源码；
- Bundle 不等于运行时插件；
- Profile 不等于 Bundle；
- Patch 不等于插件实现；
- Plugin Market Index 中列出的可安装 Bundle，不等于 Cordis 运行时 Registry；
- inject 不等于普通静态 import；
- Event 不等于所有插件协作的唯一机制；
- Cordis 不等于 Agent Loop、MCP 或操作系统沙箱；
- Effect 清理不等于自动回滚数据库事务或外部业务操作；
- ctx.get 的可选查询不等于 inject 的响应式依赖。

### 阶段 C｜真实产品插件案例（当前唯一执行任务）

**目标：** 把阶段 B 的 Cordis 抽象映射到 DeepSeek Harness 的真实产品代码，选出一个最适合技术分享的主案例。

候选：

1. **Bash 三角色组合**
   - dsh-shell：Service Definition；
   - dsh-bash-local：Provider；
   - dsh-tool-bash：Consumer。
   - 优势：直观展示接口、实现、消费者分离，以及替换 Provider 后 Consumer 不必改变。
   - 风险：涉及三个角色，不应误讲成一个插件文件。

2. **LLM Provider Adapter**
   - 例如 dsh-llm-pi-ai；
   - 优势：展示模型适配器如何接入统一 LLM 服务。
   - 风险：协议、模型路由和凭据细节可能分散主题。

3. **Agent Loop**
   - dsh-agent-loop；
   - 优势：能直接证明 Agent Loop 这样的核心产品能力也可以是插件。
   - 风险：核心依赖多、实现范围大，容易变成 Agent Loop 专题。

4. **Tutorial greet-tool**
   - 优势：最小示例，适合辅助解释；
   - 风险：不是实际产品插件，不应替代真实产品案例。

#### C1. 先做候选比较

比较每个候选：
- 配置入口和实际挂载方式；
- 插件入口形态；
- inject 依赖数量和依赖关系；
- 提供/消费哪些 Service；
- 注册哪些能力；
- 生命周期和清理逻辑；
- 相关测试数量及关键断言；
- 需要阅读的核心文件数量；
- 能否用一张图讲清楚；
- 是否需要真实 API Key 或外部服务。

不要只按代码复杂度或“核心程度”选择。优先选择讲解价值高、源码范围可控、测试证据完整的案例。

#### C2. 选定主案例后追踪完整链路

至少追踪：
1. 产品组合配置中该插件从哪里进入；
2. Loader 如何导入并创建 Fiber；
3. 插件声明了哪些依赖；
4. 依赖服务由谁提供；
5. 插件如何注册或消费能力；
6. 运行时其他插件如何调用它；
7. 插件卸载或 Provider 替换时发生什么；
8. 测试如何验证关键行为。

必须区分：
- Cordis 框架负责的通用机制；
- Harness 产品层负责的组合逻辑；
- 案例插件自己的业务实现。

## 6. 证据规范

每个重要结论必须标记：
- OFFICIAL：官方文档直接说明；
- SOURCE：固定 Commit 源码直接证明；
- TEST：固定 Commit 测试断言覆盖；
- RUN：明确环境下实际运行观察；
- ANALYSIS：基于证据形成的工程解释；
- OPEN：证据不足或存在歧义。

每条记录包含结论、证据等级、文件路径、章节/符号/行号、固定 Commit URL、证据支持范围和不能推断的内容。

禁止：
- 只贴仓库目录而不指向具体位置；
- 把文档描述冒充源码事实；
- 把测试名称冒充测试结论；
- 把推断写成官方动机；
- 把没有运行的实验写成 RUN；
- 混用上游 Cordis master 与 Harness vendored 版本。
