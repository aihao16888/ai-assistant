## 1. 为什么要做这项研究

这是一项真实的技术分享任务：需要面向同事，讲清楚 DeepSeek Harness 的核心设计主题：

**Everything is a Plugin：DeepSeek Harness 的插件化架构与实现机制。**

我们不是为了“读完一个 GitHub 仓库”，也不是为了开发一个插件，更不是把官方文档改写成一篇长摘要。

真正要解决的问题是：

> 如何借助 AI Agent，从一个自己尚不熟悉的开源项目出发，通过官方资料、固定版本源码、测试和必要的运行验证，逐步建立准确的技术理解，最后能够独立解释设计、画出架构图、回答技术问题，并完成一场有证据支撑的内部分享？

研究应当帮助研究者从“不知道它是什么”走到能够：

1. 用通俗但准确的语言解释 Everything is a Plugin 的含义和边界；
2. 解释 Cordis 如何组织插件、上下文、服务依赖、事件和生命周期；
3. 从固定版本源码追踪真实产品插件的加载、依赖、能力注册和卸载过程；
4. 用测试断言或必要的实际运行验证关键行为；
5. 画出与源码一致的架构图和调用链；
6. 分析这种设计解决了什么问题、引入了什么复杂度、适用于什么场景；
7. 面向同事完成一场约 15–20 分钟的技术分享，并能回答追问。

**研究价值不以阅读了多少文件、写了多少字衡量，而以结论是否准确、是否能追溯、是否能讲清楚和是否经得起质疑衡量。**

## 5. 研究方法：围绕问题建立证据链

禁止按文件目录机械阅读，也禁止为了证明“看过整个仓库”而全量扫描。

每个研究问题按以下步骤执行：

1. **提出问题：** 明确要解释的行为、设计或边界，说明它与分享主题的关系。
2. **查官方资料：** 找到产品文档、架构说明、开发指南或 API 契约。
3. **定位实现：** 在固定 Commit 中找到实际源码入口、关键符号和调用链。
4. **核对测试：** 阅读对应测试的具体 Arrange / Act / Assert，确认测试真正证明了什么。
5. **决定是否运行：** 只有静态证据无法回答关键问题时，才设计最小、可重复的运行验证；不得为了“跑测试”而引入不必要的环境和外部依赖。
6. **形成解释：** 用自己的语言说明机制、触发条件、状态变化和结果。
7. **写明边界：** 记录证据不能证明什么、尚未验证什么，以及是否需要进一步调查。

每次扩大资料范围前，必须先写清楚：

- 当前未解决的问题；
- 新增资料能够回答什么；
- 为什么已有资料不足；
- 预期新增的证据或结论。

如果新增资料不能回答一个明确问题，就不应扩大范围。

## 6. 必须区分的概念和证据边界

研究和写作中必须避免以下混淆：

- Plugin 不等于 Service；
- Plugin 不等于 npm package；
- Cordis 配置项不等于插件源码；
- Bundle 不等于运行时插件；
- Profile 不等于 Bundle；
- Patch 不等于插件实现；
- Plugin Market Index 中列出的可安装 Bundle，不等于 Cordis 运行时 Registry；
- inject 不等于普通静态 import；
- `ctx.get()` 的可选查询不等于 inject 的响应式依赖；
- Event 不等于所有插件协作的唯一机制；
- Cordis 不等于 Agent Loop、MCP 或操作系统沙箱；
- Effect 清理不等于自动回滚数据库事务或外部业务操作；
- Harness vendored Cordis 的实际行为不能直接用上游最新版文档代替；
- “一切皆插件”不能扩大解释为每个函数、每个文件、每个 API 或每个外部软件都必须成为插件。

对 Cordis、Koishi 和 DeepSeek Harness 的关系，必须区分直接来源证据、上游历史背景和工程推断；没有 DeepSeek 官方直接声明时，不得声称 DeepSeek 明确“参考 Koishi”。

## 7. 证据规范

每条重要结论必须标记证据类型：

| 标记 | 含义 | 允许的表述 |
|---|---|---|
| OFFICIAL | 固定版本官方文档明确说明 | “官方文档说明……” |
| SOURCE | 固定 Commit 源码直接显示 | “该版本源码中……” |
| TEST | 固定 Commit 测试断言覆盖 | “该测试验证了……” |
| RUN | 在明确环境中实际执行并观察 | “在所记录环境中实际观察到……” |
| ANALYSIS | 根据已有证据作出的工程解释 | “据此可以分析/推断……” |
| OPEN | 证据不足、行为有歧义或尚未验证 | “目前尚不能确认……” |

每条重要证据至少记录：

- 结论或待回答问题；
- 证据等级；
- 仓库、固定 Commit；
- 文件路径；
- 关键符号、章节或行号；
- 指向固定版本的链接；
- 证据具体支持的范围；
- 不能据此推断的内容；
- 如有冲突，记录冲突来源和处理方式。

禁止：

- 只贴目录或文件名，不定位具体实现；
- 把文档描述冒充源码事实；
- 把测试名称冒充测试结论；
- 把测试代码已阅读写成测试已运行；
- 把没有执行的实验写成 RUN；
- 把工程推断写成官方设计动机；
- 把上游 Cordis 行为直接当作 Harness vendored 版本行为；
- 为了让结论完整而填补证据空白。

### 阶段 C｜追踪一个真实产品插件（当前唯一待执行阶段）

**目标：** 将阶段 B 的 Cordis 抽象映射到 DeepSeek Harness 的真实产品代码，选择一个最适合技术分享的主案例。

候选方向：

1. **Bash 三角色组合**
   - dsh-shell：Service Definition；
   - dsh-bash-local：Provider；
   - dsh-tool-bash：Consumer。
   - 价值：最直观展示接口、实现和消费者分离，以及替换 Provider 时 Consumer 可以保持不变。
   - 风险：涉及三个角色，不能误讲成单个插件文件。

2. **LLM Provider Adapter**
   - 例如 dsh-llm-pi-ai。
   - 价值：展示模型适配器如何接入统一 LLM 服务。
   - 风险：模型协议、路由和凭据细节可能分散分享主题。

3. **Agent Loop**
   - dsh-agent-loop。
   - 价值：直接说明 Agent Loop 这样的核心产品能力也可以由插件提供。
   - 风险：依赖多、实现范围大，容易偏离插件化主线。

#### C1. 候选比较

先比较，不要一开始就深入全部候选。每个候选检查：

- 产品配置入口和实际挂载方式；
- 插件入口及其运行时角色；
- inject 依赖及依赖提供方；
- 提供或消费的 Service；
- 注册或暴露的能力；
- 生命周期和清理逻辑；
- 对应测试及关键断言；
- 需要阅读的核心文件数量；
- 是否需要 API Key、网络或外部服务；
- 是否能够用一张图讲清楚；
- 与 Everything is a Plugin 主旨的关联程度。

优先选择：讲解价值高、源码范围可控、证据链完整、无需外部服务即可解释核心机制的案例。比较结果和选择理由必须留档。

#### C2. 追踪选定案例的完整链路

只对最终选定的一个主案例做深入追踪：

1. 产品组合配置中，该能力从哪里进入；
2. Loader 如何导入模块、解析配置并创建 Fiber；
3. 插件声明了哪些依赖；
4. 依赖 Service 由哪个插件提供；
5. 插件如何注册、提供或消费能力；
6. 其他插件如何使用该能力；
7. Provider 替换、依赖缺失或插件卸载时发生什么；
8. 对应测试如何验证这些行为；
9. 哪些机制来自 Cordis 通用框架，哪些属于 Harness 产品组合逻辑，哪些属于案例插件自己的实现。

不得把“包”“插件”“服务定义”“Provider”“Consumer”和“Bundle”混为同一个对象。
