# 个人经历素材库

> 当前状态：初始版本，待用户审计。  
> 目标：把做过的项目转化为真实、具体、可追问、可核验的面试素材。

## 1. 为什么单独建立个人素材库？

招聘要求描述的是企业希望候选人具备什么；个人素材库记录的是自己实际做过什么。两者需要匹配，但不能混为一谈。

项目素材不能只写“使用 Redis、RabbitMQ、PostgreSQL”，而要讲清楚：

- 系统解决什么业务问题？
- 为什么出现这个问题？
- 自己负责哪个模块、做了哪些工作？
- 为什么选择这项技术？
- 技术在业务流程中的具体位置是什么？
- 遇到过什么异常或线上问题？
- 如何定位、解决和验证？
- 有哪些结果可以证明？如果没有量化结果，就不编造。

## 2. 一个项目的标准素材结构

每个项目单独维护一份文档：

1. 项目背景与业务目标。
2. 系统用户、核心业务对象和主要流程。
3. 系统架构（只记录确认过的拓扑）。
4. 本人职责与负责边界。
5. 关键业务模块。
6. 技术栈及各技术的具体用途。
7. 典型技术故事：背景、问题、分析、方案、实现、结果。
8. 失败场景与异常处理。
9. 可核验的证据清单。
10. 60 秒、2 分钟和深入追问三个层次的项目表达。
11. 待核实问题。

## 4. 个人技术栈盘点

- [技术栈与实践边界盘点](./technology-stack-inventory.md)

这份盘点把技术分为：
- 生产项目实际使用；
- 实际接触但理解尚不深入；
- 个人学习或实验；
- 仅理论了解；
- 尚未实践，不应写成项目经验。

## 5. 面试素材的质量标准

一个合格的项目故事至少要能回答：

- **Why**：为什么要做？
- **What**：解决了什么具体问题？
- **How**：技术方案怎么工作？
- **Trade-off**：为什么这样设计，有什么代价？
- **Failure**：如果超时、重复、宕机、消息丢失或数据不一致怎么办？
- **Evidence**：有什么真实证据？
- **Ownership**：本人实际负责什么？

没有真实数据时，可以说明业务结果或流程改善，但不能虚构性能提升比例、QPS、数据规模和故障恢复时间。
