# Java 后端工程师面试准备

> 主题目录｜创建日期：2026-11-23  
> 目标：把真实项目经历整理成可讲述、可追问、可核验的面试材料，而不是堆砌技术名词。

## 1. 整理原则

本目录围绕真实项目经历建立技术专题。每个专题统一采用以下结构：

1. **业务背景**：系统为什么需要这项能力，业务规模和约束是什么。
2. **问题与风险**：原方案遇到了什么问题，根因是什么。
3. **实际实现**：项目中真实采用了什么技术、数据结构和调用流程。
4. **专业原理**：相关技术为什么有效，边界和失效条件是什么。
5. **大白话解释**：能够让非当前技术栈的面试官听懂。
6. **面试问答**：主问题、追问、标准回答。
7. **验证边界**：区分已经确认的项目事实、基于事实的原理解释、尚待代码或配置核实的细节。

**重要要求：不能把建议方案写成项目已经实现的事实。** 对锁粒度、Redis 命令、事务顺序、数据库约束、异常恢复等未核实细节，必须明确标记。

## 2. 项目主线

### 2.1 文档管理系统（DMS）

这是当前重点整理的后端项目案例。系统用于企业文档全生命周期管理，涉及技术文件、工艺文件、图纸和管理文件等，业务环节包括审批、受控发布、版本管理、权限控制、归档、检索及第三方系统交互。

当前优先整理的技术故事：

| 专题 | 业务问题 | 重点技术 |
|---|---|---|
| 文档安全编码生成 | 多部门并发生成编号，完整安全编码必须全局唯一 | Java 并发、Redis 分布式锁、缓存、原子计数器、数据库持久化 |
| 重复受控发布防护 | 相同文件编号短时间内重复提交，不能重复发起流程 | Redis 防重、幂等性、并发控制、状态校验 |
| OA 审批节点同步 | OA 审批流转后，DMS 需要识别审批节点并同步业务状态 | RabbitMQ、消息消费、第三方系统集成、幂等消费 |
| 数据类型与查询问题 | PostgreSQL 组件 ID 为 Long，而 Java 曾使用 String，导致查询异常 | Java 类型映射、JDBC/MyBatis 参数类型、SQL 等值匹配 |
| 文档检索 | 大量文档需要按业务条件检索 | Elasticsearch、索引与查询设计 |
| 版本与权限 | 多人协作时需要控制版本、数据范围和操作权限 | 数据建模、事务、权限模型、状态机 |

### 2.2 建设项目管理平台

另一条项目主线是汽车制造业建设项目管理平台，面向集团多个基地和厂房，覆盖厂房、楼层、区域、产品/产线等资产，以及场地需求、租赁、会议、项目进度和风险管理。

后续可整理的专题：

- 复杂业务建模与模块边界；
- 多角色权限和数据范围；
- 需求、评审、审批、执行等流程状态管理；
- 多模块之间的数据关联与查询；
- 微服务拆分、服务间调用和系统集成（以实际架构为准）。

## 3. 当前阶段：文档安全编码与 Redis 并发控制

<badge>当前整理中</badge>

入口文档：[文档安全编码生成与 Redis 并发控制](./01-document-code-generation-and-redis-concurrency.md)

本专题要讲清楚的完整链路：

`业务全局唯一要求 → 编号序列范围 → Java 本地并发控制 → Redis 分布式锁 → Redis 缓存计数器 → 序号递增 → 生成安全编码 → 数据库持久化 → 异常恢复与唯一性兜底`

当前已经确认的业务信息：

- 安全编码由后台生成，不由用户手工填写。
- 安全编码由组织代号、车型代号、年月和递增序号等部分拼接，中间使用连字符。
- 完整安全编码要求系统全局唯一。
- 数据库有专门的序号表，记录最新序号。
- 一次请求可能生成 50 个编号。
- 同一编号分配范围发生并发请求时，需要通过锁控制生成过程。
- 系统既有 Java 本地锁，也使用 Redis 分布式锁。
- Redis 同时参与缓存序号、递增序号和后续数据库同步。

尚待核实的实现细节已列在专题文档中，不能在面试中把推测当作实际实现。

## 5. 面试表达要求

- 先用一句话概括结论，再展开业务背景和技术原理，最后总结关键点。
- 每个技术点先给出**专业术语解释**，再给出**大白话解释**。
- 讲项目时明确“我负责了什么”，不要把团队整体工作全部说成个人独立完成。
- 说明技术方案的适用条件和失败边界，不只讲 happy path。
- 对尚未核实的实现细节，使用“从当前业务描述推断”“需要结合代码确认”等表达。
- 优先讲透少数真实案例，避免泛泛罗列技术名词。
