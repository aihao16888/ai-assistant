# Java 并发与锁

> 优先级：**P0 必须掌握**  
> 当前掌握状态：S1（初始估计，待审计）  
> 关联项目：DMS 安全编码批量生成、重复提交防护

## 1. 一句话结论

Java 并发控制解决的是：多个线程同时访问共享数据时，如何避免竞态条件，让业务操作按照预期执行；但 Java 本地锁只在当前 JVM 进程内有效，不能单独协调多台服务器。

## 2. 必须理解的基础概念

### 2.1 进程与线程

**专业解释：** 进程是操作系统分配资源和隔离运行环境的基本单位；线程是进程内的执行单元。同一个进程中的多个线程通常共享堆内存等进程资源，但拥有各自的线程栈和执行上下文。

**大白话：** 进程像一家公司，线程像公司里的员工。员工可以同时工作，也可能同时修改公司共享的同一份资料。

为什么重要：一个 Java 服务进程中可以有多个请求线程。它们可能同时读取和更新同一个编号计数器、订单状态或缓存对象。

### 2.2 竞态条件（Race Condition）

**专业解释：** 程序结果依赖多个并发操作的执行时序，而操作之间缺乏足够同步，导致结果不确定。

例如两个线程都执行“读取序号 100 → 加 1 → 写回 101”，最终可能只写入 101 一次，而不是正确得到 102。

**大白话：** 两个人同时看见“下一个号是 101”，然后都把 101 发给不同请求，编号就重复了。

### 2.3 原子性、可见性和有序性

- **原子性（Atomicity）**：一个操作要么完整发生，要么不发生；不会暴露中间状态。
- **可见性（Visibility）**：一个线程修改共享变量后，其他线程能在符合内存模型规则的情况下看到更新。
- **有序性（Ordering）**：编译器、CPU 和运行时可能重排指令；同步规则需要保证关键操作的先后关系。

Java 内存模型（JMM）定义了多线程读写共享变量的可见性和有序性规则。锁、volatile、final、安全发布等机制分别解决不同问题。

**大白话：** 不只是“两个线程同时改”会出问题；一个线程改完，另一个线程看不到，或者代码执行顺序与直觉不同，也可能出问题。

## 3. synchronized 与 ReentrantLock

### 3.1 synchronized

**专业解释：** synchronized 是 Java 内置监视器锁机制，可用于方法或代码块。进入同步区域前需要获得对应监视器，退出同步区域时释放锁；同一监视器上的互斥访问也建立相应的 happens-before 关系。

**大白话：** 给一段代码加一道门，同一时刻只允许拿到这把门钥匙的线程进入。

### 3.2 ReentrantLock

**专业解释：** ReentrantLock 是显式锁实现，提供 lock/unlock、可中断获取、限时获取、公平锁选项和多个 Condition 等能力。使用时必须在 finally 中释放锁。

~~~java
lock.lock();
try {
    // 访问共享状态的临界区
} finally {
    lock.unlock();
}
~~~

**大白话：** 它也是一把锁，但比 synchronized 提供更多控制方式；使用者需要自己负责在异常时把锁释放。

### 3.3 两者怎么选？

- 简单的互斥区域，synchronized 通常足够。
- 需要 tryLock、超时等待、可中断、公平性或多个条件队列时，可以考虑 ReentrantLock。
- 不能为了“看起来高级”而盲目使用显式锁。
- 锁粒度要尽量小，但必须覆盖完整的共享状态更新过程。

## 4. 为什么本地锁无法解决多服务器并发？

假设系统部署了三个 Java 服务实例：

~~~text
请求 A → 应用实例 1 → JVM 本地锁 A
请求 B → 应用实例 2 → JVM 本地锁 B
请求 C → 应用实例 3 → JVM 本地锁 C
~~~

每个 JVM 都有自己的内存和锁对象。实例 1 的 synchronized/ReentrantLock 不会自动让实例 2、3 等待。

**专业解释：** JVM 本地锁的协调范围是单个进程。跨进程的互斥需要共享协调设施，例如 Redis 分布式锁、数据库锁或专门的协调服务。

**大白话：** 三台服务器各有一把自己的锁。第一台把门锁上，第二台并不知道，所以它也能进入。要让三台服务器都遵守同一把锁，需要一个大家都能访问的协调点。

## 5. DMS 项目如何映射？

当前已确认：安全编码由后台生成；一次请求可能批量生成约 20–50 个编号；多个请求可能竞争同一序号范围；项目使用 Java 本地锁和 Redis 分布式锁。

因此，Java 本地锁的作用可以解释为：先控制当前应用实例内部的线程竞争，避免同一个 JVM 中的多个请求同时进入编号生成临界区。

但本地锁不是跨服务器唯一性的最终保证。跨实例协调要依靠 Redis 分布式锁或数据库原子更新等共享机制。

## 6. 还必须理解的并发问题

### 6.1 锁粒度

锁粒度决定哪些请求会互相等待。

- 锁太粗：不同车型、不同月份或不同业务范围也可能被迫排队，吞吐量下降。
- 锁太细：如果本来应该共享一个序列的请求使用不同锁 Key，就可能同时修改同一序号，失去互斥效果。

正确锁粒度必须与“序号唯一性范围”一致。DMS 的具体锁 Key 维度待核实。

### 6.2 死锁

多个线程以不同顺序持有多把锁并互相等待，可能形成死锁。

常见预防方式：
- 固定获取锁的顺序；
- 避免持锁期间执行不必要的远程调用；
- 使用有界等待；
- 缩小临界区；
- 分析线程转储和锁等待链路。

### 6.3 锁与幂等不是一回事

锁控制并发访问；幂等保证同一业务请求重复执行时，不会产生多份业务结果。一个请求即使顺序执行，也可能因用户重试而执行两次，所以仅有锁不等于业务幂等。

## 7. 面试回答示例

**问：为什么你们既有 Java 本地锁，又有 Redis 分布式锁？**

答：本地锁和分布式锁解决的协调范围不同。Java 本地锁只能控制同一个 JVM 内的线程，能够减少单实例内部对同一编号生成逻辑的并发进入；但系统有多个应用实例时，不同 JVM 的本地锁互相不可见，所以还需要 Redis 这样的共享协调机制，让不同实例竞争同一个业务范围的锁。两层锁的具体必要性和锁粒度，还要结合项目实际代码确认。
