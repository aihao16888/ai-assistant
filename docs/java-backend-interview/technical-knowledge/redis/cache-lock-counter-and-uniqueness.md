# Redis：缓存、分布式锁、原子计数与唯一序号

> 优先级：**P0 必须掌握**  
> 当前掌握状态：S1（用户已接触实际业务，但原理仍需深入）  
> 关联项目：DMS 重复受控发布防护、安全编码生成

## 1. 一句话结论

Redis 在当前 DMS 业务中至少承担三类不同职责：短时间重复请求拦截、跨应用实例的并发协调、序号缓存与递增。它们分别对应防重/幂等、分布式锁和计数器，不能把这三种作用混为一谈。

## 2. Redis 为什么适合做这些事？

**专业解释：** Redis 是以内存数据结构为核心的服务，支持 String、Hash、Set、Sorted Set、List 等数据类型，并提供原子命令、过期时间和多客户端共享访问能力。常见操作通常具有较低的访问延迟，适合缓存、计数、短期状态和分布式协调。

**大白话：** 数据库像长期保存的账本，Redis 像大家都能快速查看和修改的一块共享白板。它速度快，但不能简单认为白板上的内容永远不会丢。

Redis 不是关系型数据库的通用替代品。需要长期保存、事务约束和复杂关联查询的数据，仍应由合适的持久化存储承担。

## 3. 作用一：重复受控发布防护

### 3.1 业务问题

同一份文件可能在很短时间内被用户连续点击提交。若每次点击都启动一次受控发布流程，就可能产生重复流程或重复业务处理。

### 3.2 专业机制：基于唯一 Key 的短期防重

常见做法是构造一个业务防重 Key，例如：

~~~text
dms:publish:dedup:<document-business-id>
~~~

然后使用 Redis 的原子写入方式，例如 SET key value NX EX ttl：

- NX：仅当 Key 不存在时才写入；
- EX：设置过期时间；
- 写入成功：本次请求获得短期提交资格；
- 写入失败：Key 已存在，可以识别为重复请求。

这条命令把“检查是否存在”和“写入占位”合并成一个原子操作，避免两个请求先后 GET 都读到不存在，再同时 SET 成功。

### 3.3 大白话解释

不能先问 Redis“有没有这个文件”，再过一会儿把它记进去。因为两个请求可能同时问，两个都得到“没有”，然后都继续提交。

正确做法是把“如果没有就立刻登记”作为一个不可拆分的动作。谁先登记成功，谁获得本次提交资格；后来的请求看到 Key 已存在，就被拦截。

### 3.4 防重不等于完整幂等

短期防重主要解决重复点击。完整业务幂等还要考虑：

- 第一次请求已经提交成功，但响应在网络中丢失；
- 用户等待超时后再次请求；
- 服务处理到一半宕机；
- Redis Key 过期或被清理；
- 两个请求使用了不同的请求标识，却对应同一个业务操作。

更稳妥的业务设计通常包括：
1. 稳定的业务幂等键；
2. 原子占位或状态迁移；
3. 数据库业务状态校验；
4. 必要时建立业务唯一约束；
5. 失败后明确释放、补偿或恢复占位状态。

**DMS 待核实：** 当前只确认 Redis 被用于拦截短时间重复提交；实际是否使用 SET NX、Key 的维度、TTL、数据库状态校验和失败补偿，需要看代码。

## 4. 作用二：Redis 分布式锁

### 4.1 为什么需要分布式锁？

Java 本地锁只对一个 JVM 有效。多个服务器实例如果同时处理同一序号范围，需要一个所有实例都能访问的协调机制。

### 4.2 专业机制：SET NX PX

Redis 分布式锁的一种常见基础实现：

~~~text
SET lock:<sequence-scope> <unique-token> NX PX 30000
~~~

各部分含义：

- Key：标识某一个需要互斥访问的业务资源或序号范围。
- Value：本次持有者生成的唯一 Token。
- NX：只有 Key 不存在时才能获得锁。
- PX：设置锁租约时间，避免持有者宕机后永久占锁。

获得锁的客户端才能进入受保护的临界区。没有获得锁的客户端需要等待、重试或返回繁忙。

释放锁时不能直接无条件 DEL。因为可能发生：

1. 客户端 A 获得锁；
2. A 执行时间过长，锁过期；
3. 客户端 B 获得同一个 Key；
4. A 恢复后执行 DEL；
5. A 错误删除了 B 的锁。

所以释放时应通过 Lua 等原子操作比较 Token，只有 Key 当前仍属于自己才删除。

### 4.3 大白话解释

Redis 就像三台服务器共同使用的门卫。谁先拿到某个编号范围的通行证，谁就可以进入；其他服务器必须等。通行证有期限，防止持有者宕机后永远没人能进去。

但通行证有期限也会带来风险：如果 A 的通行证过期了，B 已经拿到新通行证，A 不能回来把 B 的通行证撕掉。所以每次领证要有独特编号，归还时核对编号。

### 4.4 锁失效会不会导致重复？

**有可能，但不是“锁一失效就必然重复”。** 需要看锁失效时业务执行到哪一步，以及有没有其他保护机制。

典型危险场景：

1. A 获得锁，开始分配序号；
2. A 执行时间超过锁 TTL；
3. 锁过期，B 获得锁；
4. A、B 在没有 fencing token 或数据库约束保护的情况下同时修改序号；
5. 如果两边基于相同旧值分配序号，就可能发生重复。

因此，分布式锁本身不是全局唯一性的绝对证明。还要考虑：
- 锁 TTL 是否足够；
- 是否有续期机制；
- 锁释放是否比较 Token；
- 临界区是否可能超时；
- 数据库是否有原子更新或唯一约束；
- 过期的旧持有者能否继续写入。

**Fencing Token（栅栏令牌）** 是更强的保护思路：每次获得锁时分配单调递增的令牌，下游存储拒绝旧令牌持有者的过期写入。它不是普通 Redis 锁自动具备的能力，也不能在未实现时声称项目已经使用。

## 5. 作用三：Redis 序号缓存与原子递增

### 5.1 缓存最新序号

当前项目描述：数据库有专门的序号表，保存对应编号范围的最新序号；Redis 缓存这个最新值，后续生成时可以减少频繁读取数据库。

**专业解释：** 这是把频繁访问的序号状态放在 Redis 中，利用内存访问降低读取开销。数据库承担持久化职责，Redis 承担运行期快速访问职责。

**大白话：** 不必每次要生成一个编号，都回数据库查一次最新序号；可以把当前值放在 Redis 里，后续先从 Redis 取。

### 5.2 原子递增

Redis 的 INCR / INCRBY 是原子命令。多个客户端同时对同一个 Key 执行 INCR，Redis 会串行处理这些命令，不会因为客户端都读到相同旧值而覆盖。

例如当前序号是 100：
- 第一个 INCR 得到 101；
- 第二个 INCR 得到 102；
- 第三个 INCR 得到 103。

批量分配时，可以考虑用 INCRBY 一次预留一段连续区间，但是否适合项目，要看是否允许跳号、批次失败如何处理，以及实际序号规则。

**重要区别：**
- INCR：Redis 服务端原子递增。
- GET → Java 中 +1 → SET：三个步骤组成的整体不是原子操作，多个请求可能覆盖彼此的更新。
- Java 锁：只约束本 JVM 内线程。
- Redis 分布式锁：协调多个客户端进入临界区。
- Redis 原子计数：保证单个计数命令本身原子执行。

它们是不同层次的机制。

### 5.3 Redis 和数据库同步

目前只确认“生成后会把 Redis 中的序号状态同步到数据库序号表”，同步的具体时机、事务边界和失败补偿尚未核实。

必须理解一个风险：

~~~text
Redis 已递增并发放编号
        ↓
应用在写回数据库前宕机
        ↓
数据库仍保存旧序号
        ↓
Redis 数据又因故障、淘汰或恢复而丢失
        ↓
系统可能从旧序号重新开始，造成重复风险
~~~

如果 Redis 是临时缓存，数据库是权威来源，就要保证缓存丢失后能够安全重建；如果 Redis 在一段时间内承担序号权威状态，就必须认真处理持久化、复制、淘汰策略、故障恢复和数据库回写失败。

一种更容易论证持久性的思路是：先通过数据库事务原子预留一段序号范围，再由应用在该范围内分配；Redis 可作为加速层，但不能让尚未持久化的序号成为唯一性保障的唯一依据。是否采用这种方案，要根据项目现状和业务允许跳号的规则决定。

## 6. 安全编码生成：把完整业务串起来

当前已知编码组成：

~~~text
组织代号-车型代号-年月-递增序号
ORG01-MODEL01-202611-000001
~~~

完整编码要求全局唯一。一次请求可能生成 20–50 个编号，多个部门可能同时申请同一序号范围。

必须先明确**序列命名空间（Sequence Namespace）**：究竟哪些字段组合后决定“共用同一个递增序列”。例如可能是组织、车型和年月的组合，也可能按业务规则采用其他范围。不能仅凭编码格式推断 Redis Key 的组成。

如果多个部门共享同一序列范围，它们必须竞争同一把锁和同一个计数器；如果业务规则允许不同部门独立计数，就必须由完整编码中的其他字段确保最终唯一。这个问题需要用户确认实际规则。

## 7. 高频面试问题与参考答案

### Q1：Redis 在你们系统中起什么作用？

答：我们主要有两类业务场景。一类是文档受控发布，用户可能短时间内对同一文件重复点击提交，我们通过 Redis 记录业务标识并拦截重复请求。另一类是安全编码生成，多个请求可能同时竞争同一个序号范围，因此使用 Redis 分布式锁协调不同应用实例，并缓存、递增当前序号，之后将序号状态同步到数据库。具体 Key、命令和异常恢复机制需要以实际代码为准。

### Q2：为什么 Redis 能实现分布式锁？

答：多个应用实例都访问同一个 Redis 服务。通过 SET NX PX 可以把“判断锁不存在并创建锁”作为原子操作，只有一个客户端能够成功获得同一个 Key。锁值还应包含唯一 Token，释放时比较 Token，防止旧持有者误删新持有者的锁。

### Q3：Redis 锁过期后怎么办？

答：锁过期可能让新的客户端获得锁，而旧客户端仍在执行，因此会出现两个执行者重叠的风险。需要合理设置 TTL、必要时续期，并通过 Token 安全释放；对于不能重复写入的关键数据，还应使用数据库原子更新、唯一约束或 fencing token 等机制保护，不能只依赖锁。

### Q4：Redis INCR 和分布式锁有什么区别？

答：INCR 解决单个计数操作的原子递增；分布式锁解决一段业务临界区的互斥访问。它们不是同一个功能。多个请求只需要独立领取计数值时，原子计数可能足够；如果递增前后还涉及读取、校验、生成和持久化等多个步骤，就需要设计更完整的并发控制。

### Q5：为什么不能只把序号放 Redis？

答：Redis 适合快速读写，但缓存数据可能因为故障、淘汰或恢复而丢失。序号一旦发放，就关系到全局唯一性，必须保证数据库持久化和恢复策略可靠。否则 Redis 丢失后从旧值恢复，就有可能重复发号。

## 8. 优先级与验收标准

**P0 必须掌握：**
- 缓存、防重、幂等、分布式锁、原子计数器的区别；
- SET NX PX 的工作机制；
- Token 校验释放锁的原因；
- 锁过期后旧持有者仍运行的风险；
- INCR 与 GET/Java + 1/SET 的原子性差别；
- Redis 与数据库同步时的数据丢失窗口；
- 序列范围、锁 Key 和计数器 Key 的一致性。

**当前状态 S1 → 目标 S3：**
- 不看资料画出两台应用服务器竞争同一个序号的过程；
- 能解释 Redis 锁获得、过期、续期和释放；
- 能分析锁失效时为什么可能重复；
- 能说明 Redis 原子递增为什么不能替代数据库持久化；
- 能针对 20–50 个编号的批量请求解释如何分配连续序号区间，以及失败时是否允许跳号。

**S4 项目证据：**
- 实际防重代码、Redis Key、TTL；
- 实际分布式锁实现及锁粒度；
- 实际递增命令或 Lua 脚本；
- 数据库序号表结构和同步事务；
- 锁过期、异常退出和 Redis 数据恢复的处理逻辑。
