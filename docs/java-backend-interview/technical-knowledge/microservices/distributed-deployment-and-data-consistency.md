# 微服务、多实例部署与数据一致性

> 优先级：**P0 必须掌握**  
> 当前掌握状态：S1（用户提到三台服务器，但部署拓扑待核实）  
> 关联项目：DMS 多服务器部署、Redis 分布式锁、数据库共享访问、OA/第三方集成

## 1. 一句话结论

多台服务器解决的是计算能力扩展和故障冗余等部署问题；微服务解决的是业务能力拆分和独立演进问题。三台服务器不自动等于微服务，也不自动保证数据正确。

## 2. 什么是多实例部署？

**专业解释：** 同一个应用服务可以运行多个实例，每个实例是独立进程，可能部署在不同服务器上。负载均衡器根据路由和健康检查，将请求分配给可用实例。

**大白话：** 同一个后端程序可以在三台机器上各运行一份。用户请求先到入口，再由入口分配给其中一台机器处理。

常见目标：
- **横向扩展**：增加实例分担请求；
- **高可用**：单个实例故障时，其他实例仍能处理请求；
- **滚动发布**：更新一个实例时，其他实例继续服务；
- **故障隔离**：减少单个实例故障对整体服务的影响。

但如果三台应用服务器共用一个单点数据库，数据库仍可能成为整个系统的单点故障。高可用需要检查完整链路，不是只数应用服务器数量。

## 3. 三台服务器是不是微服务？

不是。

- 三台服务器运行同一个 Spring Boot 应用的三个副本：这是一个服务的多实例部署。
- 三台服务器运行不同业务服务，并通过 API 或消息协作：可能是微服务架构的一部分。
- 三台服务器分别运行应用、数据库、消息中间件：这是不同基础设施角色的部署，不能仅凭数量判断微服务。

判断微服务，要看业务边界、服务是否独立部署、数据所有权、接口契约、团队职责和故障隔离等，而不是看有几台机器。

## 4. 多台应用服务器如何访问同一数据库？

常见架构：

~~~text
                 用户请求
                    ↓
              负载均衡入口
             ↙      ↓      ↘
          应用 A   应用 B   应用 C
             ↘      ↓      ↙
             同一个数据库服务
~~~

三个应用实例使用各自的数据库连接池，但连接到同一个数据库服务或数据库集群。数据库负责统一处理事务、索引、约束和并发访问。

因此，“请求打到哪台应用服务器”通常不决定数据保存在哪台应用服务器。应用实例负责执行代码，数据库负责持久化。

**大白话：** 三个窗口都在办理业务，但最后都把业务记录写进同一本账。窗口在哪台机器，不会让它自动变成三本互不相关的账。

## 5. 数据库为什么能保证数据正确？

数据库提供事务、锁、MVCC 和约束等机制，但它不能自动保证所有业务逻辑正确。

常见保护方式：

- **事务**：把多个相关数据库操作作为一个原子工作单元；
- **唯一约束**：由数据库拒绝重复的唯一键；
- **行锁**：控制多个事务对特定行的并发修改；
- **乐观锁**：通过版本号或条件更新检测并发冲突；
- **原子更新**：使用单条 SQL 完成递增或状态转换；
- **隔离级别**：限制并发事务之间的可见性。

例如安全编码如果要求唯一，数据库唯一索引可以作为最后一道防线；Redis 分布式锁用于协调应用实例，但不能替代数据库约束和持久化检查。

## 6. 服务间同步与异步调用

### 同步调用

例如 HTTP/REST 或 gRPC。调用方等待被调用方返回结果。

优点：调用关系直观，适合需要立即获得结果的查询或操作。

风险：超时、级联故障、重试导致重复副作用、服务依赖变强。

### 异步消息

例如 RabbitMQ。调用方发布事件后继续执行，消费者稍后处理。

优点：解耦、削峰、异步处理。

风险：重复投递、消息堆积、最终一致性、顺序和补偿问题。

## 7. 微服务常见基础设施概念

- **API Gateway**：统一入口，处理路由、认证、限流等横切职责。
- **Service Discovery**：服务注册与发现，帮助调用方找到服务实例。
- **Load Balancing**：把请求分配给健康实例。
- **Configuration Management**：集中管理不同环境的服务配置。
- **Circuit Breaker**：依赖服务持续失败时暂时阻断调用，避免故障扩散。
- **Timeout / Retry**：限制等待时间并对可重试错误进行有限重试。
- **Distributed Tracing**：跨服务追踪一次请求经过的调用链。
- **Idempotency**：让重复请求或消息不会重复产生业务副作用。

这些是微服务常见能力，不能在没有实际使用证据时说成 DMS 已经全部具备。

## 8. 三台服务器场景下必须追问的问题

目前只知道系统部署涉及三台服务器，不知道每台机器的实际角色。需要确认：

1. 三台服务器是否运行相同的 Java 应用？
2. 是否有 Nginx、网关或其他负载均衡入口？
3. 数据库部署在哪台机器，是单机、主从还是集群？
4. Redis 和 RabbitMQ 部署在哪里，是否高可用？
5. 三个应用实例是否共享同一个数据库和 Redis？
6. 用户会话是否依赖本地内存？如果会，跨实例如何处理？
7. 文件上传的文件存储在哪里，三个实例是否能访问同一文件？
8. 应用实例故障后，正在处理的请求和消息如何恢复？
9. 数据库是否有唯一约束、事务和备份恢复机制？

## 9. 面试回答示例

**问：你们系统部署了三台服务器，为什么？**

答：多台服务器通常是为了横向扩展和提高可用性，让请求能够分配到多个应用实例，单个实例故障时不至于让整个应用立即不可用。但我不会只凭“三台服务器”就把它称为微服务架构，还要看它们运行的是同一个服务的多个副本，还是不同业务服务。数据库通常作为独立的数据持久化层，多个应用实例通过各自的连接池访问同一个数据库服务。跨实例的并发问题不能依赖 JVM 本地锁，需要 Redis 分布式锁或数据库并发控制。

## 10. 优先级与验收标准

**P0 必须掌握：**
- 多实例部署与微服务架构的区别；
- 负载均衡、健康检查和横向扩展；
- 多个应用实例如何连接共享数据库；
- 为什么本地锁不能协调不同服务器；
- 数据库事务、唯一约束、行锁和乐观锁的作用；
- 同步调用和消息异步的适用场景及故障风险；
- 单个应用实例故障与数据库故障的影响差异。

**P1 重点理解：**
- 服务注册发现、API Gateway、熔断、限流和分布式追踪；
- 服务拆分、数据归属、最终一致性；
- 无状态服务、共享 Session、文件存储和配置管理。
