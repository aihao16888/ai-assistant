# RabbitMQ 与 OA 审批节点同步

> 优先级：**P0 必须掌握（项目故事）/ P1 重点理解（高级可靠性机制）**  
> 当前掌握状态：S1（真实接触过，但消息机制尚需系统梳理）  
> 关联项目：DMS 接收 OA 审批节点消息，并按业务条件向第三方同步数据

## 1. 一句话结论

RabbitMQ 在 OA 与 DMS 的业务链路中承担消息异步传递和系统解耦的作用：OA 流程推进产生节点消息，DMS 接收后判断当前节点和业务状态，再决定是否向第三方同步数据。

实际生产者、交换机、队列、路由键和消费确认方式需要进一步核实。

## 2. 为什么不直接让 OA 同步调用 DMS？

如果 OA 每推进一个审批节点，都直接同步调用 DMS，双方就会产生较强的运行时依赖：

- DMS 响应慢，可能拖慢 OA 的审批请求；
- DMS 短暂不可用，OA 需要承担同步失败；
- 两边发布和扩容节奏相互影响；
- 高峰期请求可能集中冲击 DMS。

消息队列提供异步缓冲：生产者把消息发送到 Broker，消费者按自己的能力处理。生产者不必等待消费者完成全部业务处理。

**大白话：** OA 不必一直等 DMS 把事情做完，可以先把“某个审批节点发生了变化”这件事交给消息队列；DMS 有能力时再取出来处理。

## 3. RabbitMQ 的核心组成

### 3.1 Producer（生产者）

负责发送消息的应用。可能是 OA 相关服务，但实际发布者需要核实。

### 3.2 Exchange（交换机）

生产者通常把消息发送给 Exchange，而不是直接指定某个消费者。Exchange 根据类型和 Binding 规则，把消息路由到一个或多个 Queue。

常见类型：
- **Direct**：按 Routing Key 精确匹配；
- **Topic**：按通配规则匹配 Routing Key；
- **Fanout**：广播到绑定队列；
- **Headers**：根据消息头属性匹配。

### 3.3 Queue（队列）

消息等待消费的缓冲区。队列是否持久化、消息是否持久化、是否配置死信交换机，都影响消息在故障场景下的表现。

### 3.4 Consumer（消费者）

从队列取消息并执行处理逻辑。DMS 可能作为消费者接收审批节点消息，具体实现需核实。

### 3.5 Binding 与 Routing Key

Binding 定义交换机到队列的路由关系；Routing Key 是生产者发布消息时携带的路由标识。它们共同决定消息进入哪些队列。

## 4. DMS 的业务链路

根据目前描述，业务链路可以先表达为：

~~~text
OA 流程引擎推进审批节点
        ↓
产生审批节点相关消息
        ↓
消息经 RabbitMQ 传递
        ↓
DMS 消费消息
        ↓
解析流程实例、业务标识、当前节点等信息
        ↓
判断是否为需要处理的目标审批节点
        ↓
满足条件：向第三方同步对应数据
不满足条件：按业务规则更新/记录状态或忽略
~~~

需要注意：以上是业务逻辑结构，不代表实际消息字段和处理状态已经核验。

## 5. 为什么消息消费必须考虑重复？

RabbitMQ 常见可靠消费模式会允许消息重新投递。例如消费者处理完成但 ACK 没有成功到达 Broker，Broker 可能再次投递该消息。

因此消费者可能收到重复消息。

**专业术语：At-least-once Delivery（至少一次投递）**，表示在特定可靠性配置下，消息可能被重复投递；业务消费者必须能够安全处理重复事件。

**大白话：** 消息队列为了避免消息丢失，可能会再送一次。DMS 不能因为“我只想处理一次”就假设消息一定只来一次。

常见幂等方法：
- 使用消息 ID 或业务事件 ID 记录已处理状态；
- 使用流程实例 ID + 节点 ID + 业务版本等构造幂等键；
- 将“检查是否处理过”和“业务状态更新”放在数据库事务中；
- 对第三方接口传递稳定的幂等请求标识（如果对方支持）；
- 对重复消息返回成功 ACK，但不重复执行业务副作用。

## 6. 消息确认、失败重试和死信队列

### 6.1 ACK

手动 ACK 模式下，消费者在业务处理成功后向 Broker 确认消息。若处理失败或消费者断开，消息可能重新入队或按配置进入其他处理路径。

不能在业务尚未成功时过早 ACK，否则进程崩溃后可能造成消息丢失。

### 6.2 Publisher Confirm

生产者确认机制用于判断 Broker 是否确认接收发布消息。它与消费者 ACK 不是一回事：

- Publisher Confirm：生产者到 Broker 的发布确认；
- Consumer ACK：消费者处理消息后向 Broker 确认。

### 6.3 Retry 与 DLQ

失败重试适合处理短暂性故障，例如第三方系统短暂超时。但无限立即重试可能造成消息堆积和系统雪崩。

常见方案：
- 限制重试次数；
- 设置退避时间；
- 对不可恢复错误进入死信队列（Dead Letter Queue, DLQ）；
- 记录失败原因并提供人工补偿或重新投递流程。

## 7. 数据库事务与消息的一致性

一个常见问题：业务数据库已经更新，但消息没有成功发布；或者消息已发布，但数据库事务随后回滚。

**Transactional Outbox（事务发件箱）** 是一种常见解决思路：在同一个数据库事务中同时写业务数据和待发布事件记录，再由独立任务可靠发布事件。它可以减少数据库更新与消息发布之间的双写不一致窗口。

这只是通用方案，不代表 DMS 当前已经使用 Outbox。

## 8. 面试回答示例

**问：你们为什么使用 RabbitMQ？**

答：我们的 DMS 与 OA 流程引擎有审批节点同步需求。OA 流程每推进到相关节点，就需要把流程事件传递给 DMS。DMS 接收到消息后，根据当前节点和业务条件判断是否需要继续向第三方同步数据。使用 RabbitMQ 可以把流程事件传递和后续业务处理解耦，避免 OA 与 DMS 的处理强耦合。面试中还需要进一步说明生产者、队列路由、消费者确认、失败重试和幂等处理的实际实现。
