# 文档安全编码生成与 Redis 并发控制

> 面试专题｜更新日期：2026-11-23  
> 关联项目：企业文档管理系统（DMS）  
> 本文目标：讲清楚后台自动生成全局唯一安全编码时，为什么需要 Java 本地锁、Redis 分布式锁、Redis 缓存计数器和数据库序号表。

## 0. 先给结论

这是一个**分布式环境下的唯一编号生成与并发控制问题**。

系统后台自动生成安全编码。安全编码由组织代号、车型代号、年月和递增序号等部分拼接而成；数据库有专门的序号表记录最新序号。由于多个部门或多个应用实例可能同时为相同编号范围申请编号，如果它们同时读取到同一个旧序号，就可能生成相同的末尾序号，最终导致完整安全编码冲突。

当前业务描述确认系统同时使用 Java 本地锁和 Redis 分布式锁；Redis 还用于缓存当前序号、执行递增，并在生成后将序号状态同步到数据库。

可以先这样记：

- **Java 本地锁**：控制同一个 JVM 内的线程竞争。
- **Redis 分布式锁**：控制不同服务器实例对同一编号分配范围的并发访问。
- **Redis 缓存**：缓存数据库序号表中的最新序号，减少数据库读取。
- **Redis 原子计数器**：在同一个 Redis Key 上执行递增，避免并发读取—计算—写入造成重复分配。
- **数据库序号表**：保存持久化的序号状态。
- **数据库唯一约束**：如果对完整安全编码建立了唯一索引，可以作为最终防线；是否已经建立，需要核对实际表结构。

注意：上面是对目前业务描述的归纳。Redis Key 的具体维度、使用的命令、数据库同步时机和异常恢复方式，仍需以实际代码、配置和表结构为准。

## 1. 业务背景：为什么需要安全编码？

### 1.1 编码结构

目前描述的安全编码由多个字段拼接，中间使用连字符：

```text
组织代号-车型代号-年月-递增序号
ORG01-MODEL01-202611-000001
ORG01-MODEL01-202611-000002
ORG01-MODEL01-202611-000003
```

以上只是结构示意，不代表真实字段长度或实际编码样例。

各部分的业务含义：

| 组成部分 | 含义 |
|---|---|
| 组织代号 | 标识所属组织 |
| 车型代号 | 标识对应车型 |
| 年月 | 标识编号所属时间范围 |
| 递增序号 | 在相应编号范围内依次递增 |

### 1.2 两种唯一性要区分

**完整安全编码的全局唯一性（Global Uniqueness）**

系统中不能出现两条完全相同的安全编码。它还用于与第三方系统交互，因此不仅是页面展示编号。

**末尾序号在编号范围内的唯一性（Sequence Uniqueness within a Namespace）**

末尾序号通常是在某个编号范围内递增。这个范围可能由组织、车型、年月或其他业务维度共同确定，必须以系统实际规则为准。

因此，“完整安全编码全局唯一”不等于“末尾数字必须在整个系统中全局唯一”。例如，不同编号范围是否允许都从 000001 开始，要看业务规则。

### 1.3 为什么会发生重复？

假设某个编号范围当前最新序号是 100，需要一次生成 50 个编号。

没有并发控制时：

1. 请求 A 查询到最新序号 100。
2. 请求 B 几乎同时查询到最新序号 100。
3. A 根据 100 生成 101～150。
4. B 也根据 100 生成 101～150。
5. 两个请求产生重复序号。

根因不是“序号加一”这个计算本身有问题，而是**读取最新值、计算新值和更新最新值这一组操作不是原子整体**。

这属于典型的并发竞争（Race Condition）。

## 2. 核心专业术语：先把概念讲准确

| 专业术语 | 专业解释 | 大白话解释 |
|---|---|---|
| Race Condition（竞态条件） | 多个线程或进程并发访问共享状态，执行顺序影响最终结果 | 两个人同时看见最新号是 100，都以为下一个号归自己 |
| Critical Section（临界区） | 访问共享资源、必须受到并发保护的代码区域 | 生成这批编号时，别人不能同时改同一份序号状态 |
| JVM Local Lock（本地锁） | 只在一个 JVM 进程内生效的互斥机制 | 只能管住同一台应用服务器里的线程 |
| Distributed Lock（分布式锁） | 多个进程通过共享协调存储，对同一资源实现互斥访问 | 多台应用服务器共同遵守同一把锁 |
| Cache（缓存） | 将热点数据保存在更快的存储中，减少后端存储访问 | 数据库里的最新序号先放一份在 Redis，后续直接读取 |
| Atomic Counter（原子计数器） | 递增操作作为不可分割的整体执行 | 多个人同时加号，也不会拿到同一个递增结果 |
| Persistent Storage（持久化存储） | 将状态保存到具备持久化能力的数据存储中 | Redis 里的运行状态最终要有可靠的数据库记录 |
| Unique Constraint（唯一约束） | 数据库拒绝违反唯一性规则的写入 | 即使应用层出了错，数据库也不允许重复安全编码入库 |
| Idempotency（幂等性） | 同一业务请求执行一次或多次，业务结果保持一致 | 用户重复点提交，不会产生多份相同业务结果 |

## 3. Redis 在这个业务中承担哪几个职责？

### 3.1 职责一：Distributed Lock（分布式锁）

**专业解释**

分布式锁用于在多个应用实例之间建立互斥关系。所有实例针对同一编号分配范围，必须竞争同一个 Redis 锁 Key。某个请求获取锁后，其他请求不能同时进入受保护的临界区。

**大白话解释**

假设服务器 A、B、C 都可能生成某个车型的编号。A 先拿到 Redis 里的锁，就由 A 先处理这批编号；B、C 必须等 A 释放锁后再竞争。这样不会出现三个服务器同时读取和修改同一份序号状态。

**锁住的究竟是谁？**

不是锁住 Redis 服务，也不是锁住数据库表，而是锁住“某个编号分配范围对应的业务临界区”。

锁的持有者是发起编号生成请求、并成功获取锁的应用线程/任务。Redis 保存锁的状态并协调其他实例。

锁 Key 示意：

```text
lock:document:sequence:<编号分配范围>
```

例如，若实际编号范围按车型和年月区分，可以设计为：

```text
lock:document:sequence:MODEL01:202611
```

这只是示例。实际 Key 必须与序号表的业务唯一维度一致，不能在未看代码前断言系统使用了这个 Key。

**锁粒度为什么重要？**

- 锁范围太大：不同车型、不同编号范围也互相等待，并发能力下降。
- 锁范围太小：本应共享同一序号的请求使用不同锁，仍可能产生重复。
- 正确做法：锁的 Key 与业务序号的分配范围保持一致。

### 3.2 职责二：Cache（序号缓存）

**专业解释**

将数据库序号表中的最新序号缓存在 Redis。缓存命中时，编号生成逻辑可以直接访问 Redis，减少数据库查询；缓存未命中时，需要从数据库读取持久化的最新序号并初始化缓存。

**大白话解释**

数据库是长期保存序号的地方，但每次生成编号都查数据库会增加数据库访问。于是把当前最新序号放在 Redis 里，后续生成时优先从 Redis 取。

需要确认：项目实际是否采用“Redis 未命中时读取数据库并初始化”的流程，以及初始化是否有并发保护。

### 3.3 职责三：Atomic Counter（原子计数器）

**专业解释**

Redis 的 `INCR`、`INCRBY` 等命令能够对同一个 Key 执行原子递增。多个客户端并发操作同一 Key 时，Redis 会依次处理这些命令，每次递增都基于前一次操作完成后的值。

**大白话解释**

假设 Redis 当前序号是 100：

- A 执行增加 50，得到 150；
- B 再执行增加 50，得到 200。

于是 A 可以使用 101～150，B 可以使用 151～200，不会因为同时读取到 100 而分到相同区间。

命令示意：

```redis
INCRBY document:sequence:MODEL01:202611 50
```

如果命令返回 150，那么这次预留的区间可以计算为：

```text
起始序号 = 150 - 50 + 1 = 101
结束序号 = 150
```

注意：

- 这是原子号段分配的一种实现方式。
- 目前尚未确认项目实际使用 `INCR`、`INCRBY`，还是其他自增逻辑。
- 原子递增只保证同一个、未发生回退的 Redis 计数器上的递增操作不互相覆盖；它本身不保证数据库持久化，也不自动保证所有业务维度下的完整安全编码全局唯一。

### 3.4 三个职责之间的区别

| 机制 | 主要解决什么 | 是否等价 |
|---|---|---|
| 分布式锁 | 多个请求能否同时进入同一业务临界区 | 不等于计数器 |
| 缓存 | 最新序号从哪里快速读取 | 不等于锁 |
| 原子计数器 | 多个递增操作能否安全获得不同结果 | 不等于持久化 |

**最重要的一句话：锁负责互斥，缓存负责减少数据库读取，原子计数器负责安全递增。**

## 4. Java 本地锁和 Redis 分布式锁为什么同时存在？

### 4.1 JVM Local Lock（Java 本地锁）

**专业解释**

Java 本地锁只对当前 JVM 进程内共享同一个锁对象的线程有效。例如 `synchronized`、`ReentrantLock`。

**大白话解释**

一台服务器里可能同时有很多线程处理请求。本地锁可以让同一台服务器里的线程排队执行编号生成的关键代码。

但是，如果系统部署了三台服务器，每台服务器都有独立 JVM，那么 A 服务器的 `synchronized` 不会阻止 B 服务器的线程执行。

### 4.2 Distributed Lock（Redis 分布式锁）

**专业解释**

Redis 分布式锁通过共享 Redis Key 协调多个 JVM 实例。所有实例竞争同一个锁 Key，只有成功获取锁的实例可以进入受保护的临界区。

**大白话解释**

本地锁只能管理一台服务器内部的线程。Redis 锁相当于在多台服务器之间建立一个共同的排队入口。

### 4.3 为什么两层锁不能混为一谈？

假设系统部署三台服务器：

```text
服务器 A（JVM A）        服务器 B（JVM B）        服务器 C（JVM C）
线程 A1 / A2             线程 B1 / B2             线程 C1 / C2
    |                         |                         |
本地锁 A                  本地锁 B                  本地锁 C
    |                         |                         |
    +-------------------------+-------------------------+
                              |
                       Redis 分布式锁
                              |
                       同一编号分配范围
```

- A 的本地锁只能协调 A1、A2。
- B 的本地锁只能协调 B1、B2。
- C 的本地锁只能协调 C1、C2。
- Redis 分布式锁负责协调 A、B、C 三台服务器。

**补充：本地锁是否一定需要？**

不一定。如果所有应用实例都严格使用同一把实现正确的 Redis 分布式锁，本身就能实现跨实例互斥。本地锁可能用于减少同一实例内大量线程同时访问 Redis、降低锁竞争，或保护本地共享状态。它是否属于项目必需设计，要结合实际代码判断。

## 5. 当前业务可以怎样还原成完整流程？

根据目前描述，可以先抽象成以下流程。这里是**业务流程模型**，不是已经逐行核实的源码执行顺序。

### 5.1 业务流程

1. 后台收到生成安全编码的请求，例如需要生成 50 个。
2. 在当前应用实例内，通过 Java 本地锁控制本机线程竞争。
3. 通过 Redis 分布式锁竞争对应编号范围的锁。
4. 读取 Redis 中缓存的最新序号。
5. 如果 Redis 已有序号，则在 Redis 中递增；如果没有，需要从数据库序号表读取最新值并初始化缓存（这一分支需要代码核实）。
6. 根据新序号生成 50 个完整安全编码。
7. 将最新序号状态同步到数据库序号表。
8. 释放 Redis 分布式锁，再释放本地锁。

### 5.2 流程示意

```text
             后台生成编号请求（50 个）
                         |
                   Java 本地锁
                         |
                  Redis 分布式锁
                         |
                  读取 Redis 序号
                    /         \
                命中             未命中
                 |                |
              直接递增        查询数据库序号表
                 |                |
                 |             初始化 Redis
                 |                |
                 +-------+--------+
                         |
                    生成 50 个编码
                         |
                  更新数据库序号表
                         |
                    释放 Redis 锁
                         |
                    释放本地锁
```

### 5.3 “同一车型下，后一个请求要等待”意味着什么？

如果业务要求请求 A 生成 50 个编号期间，请求 B 必须等待，那么说明锁保护的范围可能覆盖整批生成过程，而不只是一次 Redis 递增。

例如：

- 当前序号 100；
- A 获得锁，生成 101～150；
- B 在锁外等待；
- A 完成生成和序号状态同步，释放锁；
- B 获得锁，再从最新状态继续生成。

这样体现的是**按编号范围串行化批次生成**。

但要区分另一种设计：通过 `INCRBY 50` 一次性预留号段后，立即释放锁。此时 B 可以很快获得 151～200，不一定需要等待 A 完成全部编码拼接。两种设计的锁持有时间和并发能力不同，不能混为一谈。

## 6. 分布式锁本身要掌握哪些机制？

### 6.1 获取锁：SET NX PX

**专业解释**

Redis 可以通过带条件和过期时间的写入命令实现基本锁语义：

```redis
SET lock:document:sequence:<scope> <unique-token> NX PX 30000
```

- `NX`：仅当 Key 不存在时设置成功。
- `PX 30000`：设置 30 秒过期时间。
- `unique-token`：当前请求唯一的持有者标识。

**大白话解释**

谁先把锁放进 Redis，谁就拿到锁。其他请求发现锁已经存在，就不能同时进入。

### 6.2 为什么锁必须有过期时间？

如果应用服务器获取锁后崩溃，无法执行释放锁的代码。没有过期时间，锁可能一直存在，后续请求都无法生成编号。

过期时间（Lease / TTL）可以在持有者异常退出后，允许其他请求重新竞争。

### 6.3 为什么释放锁不能直接 DEL？

假设：

1. A 获得锁，Token 是 A。
2. A 执行时间超过锁的 TTL，锁过期。
3. B 获得同一个锁，Token 是 B。
4. A 恢复执行，直接执行 `DEL lockKey`。

这样 A 可能把 B 的锁删除。

正确做法是：释放锁时先比较 Redis 中的 Token 是否仍然属于当前请求，只有匹配时才删除。通常使用 Lua 脚本把“比较”和“删除”合并为一个原子操作。

**大白话解释：不能因为自己曾经拿过锁，就随便把现在这把锁删掉；必须先确认它还是自己的。**

### 6.4 锁续期（Lock Renewal）

如果编号生成可能超过锁的有效期，就需要评估续期机制。

专业解释：在持有者仍然有效且拥有锁的前提下，延长租约时间，避免业务尚未完成锁就过期。

大白话：如果生成 50 个编号需要 40 秒，但锁只设置了 30 秒，就可能出现任务还没完成、锁已经自动消失的情况。

### 6.5 Fencing Token（栅栏令牌）

这是更进阶的分布式锁防护机制。

即使旧请求因为暂停、网络延迟等原因在失去锁后继续执行，也可以通过单调递增的令牌，让下游存储拒绝旧持有者的过期写入。

大白话：A 原来拿过锁，但后来锁已经交给 B。即使 A 又恢复了，也不能拿着旧通行证覆盖 B 的新结果。

是否使用 Fencing Token，需要以实际系统实现为准；它是理解锁过期风险的进阶知识，不应直接说成项目已有能力。

## 7. 最关键的故障场景：锁失效后会不会重复？

答案：**可能，但不是必然。要看计数器分配和数据库同步如何设计。**

### 7.1 情况一：锁失效，两个请求都读取数据库旧值

假设数据库最新序号是 100：

1. A 获取 Redis 锁，读取数据库的 100。
2. A 生成编号时耗时过长，锁过期。
3. B 获取锁，也读取数据库的 100。
4. A、B 都根据 100 生成 101～150。

结果：可能重复。

根因是两个请求都从同一个持久化旧值计算新序号，且没有可靠的原子分配或防止旧持有者继续执行的机制。

### 7.2 情况二：使用同一个 Redis Key 原子递增

假设 Redis 计数器一直保留正确状态，A、B 都对同一个 Key 执行 `INCRBY 50`：

- A 得到 150；
- B 得到 200。

即使 A 的锁过期，只要计数器没有丢失、回退或被错误覆盖，两次原子递增仍然会获得不同区间。

因此：

**锁过期不必然造成重复；原子计数器可以避免部分重复分配问题，但不能替代锁的正确性、持久化和故障恢复设计。**

### 7.3 情况三：Redis 数据丢失或计数器回退

假设：

- 数据库序号表最新值仍然是 100；
- Redis 已经递增到了 150；
- 编号 101～150 已经生成并被使用；
- Redis 发生数据丢失或恢复到了旧值 100；
- 系统再次从数据库读取 100。

此时可能再次分配 101～150。

这说明：如果 Redis 是运行时的热计数器，而数据库只在后面同步，那么必须设计可靠的持久化和恢复机制。

### 7.4 四个防护层次

| 防护层次 | 专业作用 | 大白话 |
|---|---|---|
| 锁 Token 校验释放 | 防止旧持有者误删新锁 | 不能把别人的锁删掉 |
| TTL 与续期 | 减少业务未完成锁已过期 | 锁不能比业务先失效 |
| 原子号段分配 / 栅栏令牌 | 避免重复分配或阻止过期持有者写入 | 旧请求不能覆盖新请求 |
| 数据库唯一约束与恢复机制 | 最终防止重复编码落库，并保证序号不回退 | 最后一道门不允许重复数据进入 |

## 8. Redis 与数据库如何保持序号一致？

这是本案例最需要谨慎表达的地方。

### 8.1 两者为什么都要存在？

**数据库序号表**

- 保存持久化的最新序号；
- 应用重启或缓存未命中时，可以作为恢复依据；
- 便于审计和查询序号状态。

**Redis 计数器**

- 缓存最新序号；
- 减少频繁访问数据库；
- 利用原子递增快速分配序号。

大白话：数据库负责长期保存，Redis 负责运行时快速读写。但 Redis 当前值和数据库已保存值可能存在时间差。

### 8.2 这属于哪一种缓存写入模式？

如果真实流程是“先更新 Redis，生成完成后再把最新序号写入数据库”，这可以理解为**Write-Behind / Write-Back（写后同步/回写）**的思路。

但要确认数据库同步是：

- 每批生成后同步；
- 定时批量同步；
- 异步消息同步；
- 还是其他方式。

不能只说“Redis 最后同步数据库”，就认为数据一致性问题已经解决。

### 8.3 两种常见的可靠性设计

**方案 A：数据库作为序号权威来源**

1. 对序号表中对应业务范围的记录加行锁，或使用原子更新。
2. 在数据库事务中预留一个号段。
3. 事务提交后，再把最新值写入 Redis 缓存。
4. 生成并使用预留的号段。
5. Redis 丢失时，重新从数据库恢复。

例如可以使用数据库原子更新或 `SELECT ... FOR UPDATE` 实现号段预留。具体 SQL 取决于数据库和表结构。

优点：数据库中的已预留序号是持久化依据。

**方案 B：Redis 作为运行时热计数器，数据库保存持久化检查点**

1. 在 Redis 中原子递增，快速获得序号或号段。
2. 生成安全编码。
3. 将最新序号可靠地同步到数据库。
4. 只有在持久化和失败处理策略满足要求后，才释放关键流程或向业务确认成功。
5. Redis 故障恢复时，必须确保计数器不会回退到已发放的旧值。

优点：减少数据库访问；风险是 Redis 与数据库之间存在同步窗口，需要解决崩溃、同步失败和数据回退。

从目前的业务描述看，更接近第二种模式，但具体写入顺序、同步机制和恢复策略仍待核实。

### 8.4 数据库唯一索引为什么仍然重要？

如果完整安全编码有唯一索引，那么即使应用层出现并发 bug，数据库也会拒绝插入重复编码。

例如：

```sql
CREATE UNIQUE INDEX uk_document_safe_code
ON document(safe_code);
```

这是示意 SQL，不代表项目当前已存在该索引。

需要注意：

- 唯一索引是最终防线，不是正常编号分配的主要手段。
- 唯一冲突后，应用要正确处理异常，不能吞掉错误。
- 如果序号状态已经错误，单纯重试插入可能持续冲突，必须先修复或重新分配序号。
- 序号表本身也应该保证同一个编号范围只有一条有效序号记录。

### 8.5 唯一性不等于绝对连续

例如，系统预留了 101～150，但在生成或保存过程中发生故障，最终只使用了 101～120。

之后从 151 开始继续使用，可能会出现 121～150 的空号。

这不一定是错误。

- 唯一性：不能重复。
- 连续性：不能跳号。
- 无空洞的连续编号：要求更严格，涉及事务、回滚和业务是否已经对外使用编号。

工程上通常先保证唯一性和不重复使用；是否要求绝对连续，需要业务明确规定。

## 9. 面试高频问题与标准答案

以下答案均采用“专业解释 + 大白话 + 面试表达”的结构。涉及未确认的项目实现时，必须按实际代码修订。

### Q1：为什么这个系统需要 Redis 分布式锁？

**专业解释**

因为应用部署在多个 JVM 实例中，Java 本地锁只能保证单个 JVM 内的互斥，无法协调其他服务器。Redis 分布式锁通过共享 Key，让多个实例针对同一个编号分配范围竞争锁，从而控制并发访问共享序号状态。

**大白话解释**

一台服务器上的锁管不了另一台服务器。Redis 是大家都能访问的公共协调点，所以多台服务器要通过 Redis 排队。

**面试表达**

> 我们的文档管理系统会根据组织、车型和年月等业务信息生成安全编码。多个部门可能同时申请同一编号范围，如果多个请求同时读取到相同的最新序号，就可能产生重复。Java 本地锁只能控制当前 JVM，所以我们还使用 Redis 分布式锁，让不同服务器实例对同一编号范围进行互斥控制，避免并发修改序号状态。

### Q2：为什么既有 Java 本地锁，又有 Redis 分布式锁？

**专业解释**

本地锁用于 JVM 进程内的线程互斥；Redis 分布式锁用于多个 JVM 实例之间的互斥。两者作用范围不同。

**大白话解释**

本地锁管一台服务器，Redis 锁管多台服务器。

**面试表达**

> 因为系统是多实例部署的。本地锁无法跨 JVM，所以需要 Redis 分布式锁实现跨节点协调。本地锁可以先控制单个实例内的线程竞争，减少同一台服务器上大量线程直接竞争 Redis 锁。真正保证跨服务器互斥的是 Redis 分布式锁。

补充：如果面试官追问“既然有 Redis 锁，本地锁是不是多余”，可以回答：从跨实例正确性角度，正确实现的 Redis 锁本身可以完成互斥，本地锁属于辅助措施，是否必要要看本地状态和锁竞争设计。

### Q3：Redis 在这个业务中究竟起什么作用？

**专业解释**

Redis 在当前业务描述中承担三个角色：分布式锁、最新序号缓存和原子计数器。锁用于并发协调，缓存用于减少数据库读取，计数器用于原子递增。

**大白话解释**

Redis 一方面负责让大家排队，另一方面保存当前最新序号，还负责安全地把序号往上加。

**面试表达**

> Redis 不只是用来加锁。它还缓存数据库序号表中的最新值，缓存命中时可以直接递增，减少数据库访问；同时利用原子递增操作，避免并发请求拿到相同的序号。分布式锁负责控制整个编号生成过程的并发访问。

### Q4：Redis 的 INCR 为什么是原子操作？

**专业解释**

Redis 对单条命令的执行具有原子性。对同一个 Key 的多个递增命令会依次执行，每次操作基于前一次完成后的值，不会出现多个客户端同时读取旧值再覆盖写入的情况。

**大白话解释**

大家同时按加一按钮，Redis 会把这些加一操作依次处理，不会两个人都拿到同一个加一结果。

**面试表达**

> 如果使用普通的 GET、应用端加一、SET，多个请求可能同时读取到相同旧值，产生覆盖。Redis 的 INCR/INCRBY 是原子递增，同一个 Key 的每次递增都能得到不同的新值，所以可以用于序号分配。

### Q5：既然 Redis INCR 是原子操作，为什么还要分布式锁？

**专业解释**

原子递增只保证单条计数器命令的原子性；分布式锁可以保护多个步骤组成的业务临界区，例如缓存初始化、序号读取、批量生成、持久化和异常处理。

**大白话解释**

INCR 只能保证“加数字”这个动作不乱，但整个业务还有读取数据库、初始化缓存、生成一批编码、同步数据库等步骤。锁是为了让这些步骤按业务要求执行。

**面试表达**

> 原子递增和分布式锁解决的问题不同。原子递增保证计数器操作本身不会发生并发覆盖；分布式锁用于保护编号生成这一整段业务流程，特别是同一编号范围的初始化、批量处理和持久化。是否需要锁住完整批次，要看业务是否要求后一个请求等待前一个批次完成。

### Q6：如果 Redis 分布式锁过期了，会不会产生重复安全编码？

**专业解释**

存在风险，但不是必然。若旧持有者和新持有者都从数据库读取同一个旧序号并自行计算，可能重复；若所有请求都通过同一个未回退的 Redis Key 原子递增分配不同号段，则单纯锁过期不一定导致序号重复。还需要考虑旧持有者继续写入、Redis 数据回退和数据库同步失败。

**大白话解释**

锁过期后，别人可能进来了。如果两个人又都按数据库里的旧数字生成，就会重复；如果每个人都通过 Redis 原子计数器拿到不同数字，就能避免这一类重复，但还得防止 Redis 数据丢失和旧请求覆盖新结果。

**面试表达**

> 锁过期确实是分布式锁的风险。我们需要设置合理的 TTL，必要时做续期，并且释放锁时校验唯一 Token，避免旧请求误删新锁。对于序号本身，还需要原子分配和数据库持久化兜底。锁只能解决互斥，不能单独保证计数器永远不回退。

### Q7：为什么 Redis 和数据库都要保存最新序号？

**专业解释**

Redis 用于缓存和高频原子操作；数据库用于持久化保存序号状态。两者之间需要定义明确的权威数据来源、同步时机和恢复策略。

**大白话解释**

Redis 读写快，数据库负责长期保存。不能只因为 Redis 里有最新值，就认为它永远不会丢。

**面试表达**

> 我们有独立的序号表保存最新序号，Redis 缓存当前值以减少数据库访问。生成后还要把最新序号同步到数据库。这里最重要的是处理两边的数据一致性，例如 Redis 更新成功但数据库同步失败，或者 Redis 故障后恢复到旧值，都不能让已经使用过的序号重新分配。

### Q8：如果 Redis 中没有当前序号怎么办？

**专业解释**

通常需要从数据库序号表读取该编号范围的最新持久化值，再初始化 Redis。初始化必须具备并发保护，避免多个实例同时读取旧值并相互覆盖。

**大白话解释**

Redis 第一次没有这个车型的计数器，就先去数据库查上次用到多少，再把这个数字放到 Redis 里继续加。

**面试表达**

> 缓存未命中时，需要从数据库读取对应编号范围的最新序号并初始化 Redis。初始化过程也要考虑并发，不能让多个请求同时读取同一个旧值再分别覆盖缓存。具体使用锁、SETNX 或数据库原子更新，需要结合项目代码确认。

### Q9：如何最终保证完整安全编码全局唯一？

**专业解释**

应从业务编号范围、并发分配、持久化和数据库约束多层保证：编号范围设计正确；并发分配使用互斥或原子号段；序号状态可靠持久化；完整安全编码设置数据库唯一约束作为最终兜底。

**大白话解释**

正常情况下，系统生成时就要保证不重复；最后数据库还要把关，任何重复编码都不能真正保存进去。

**面试表达**

> 首先要确保同一编号范围内的序号分配不会重复，再保证组织、车型、年月和序号拼接后的完整编码符合全局唯一规则。数据库层还应该通过唯一约束防止重复记录落库。具体项目是否已经建立唯一索引，需要以实际表结构为准。

### Q10：如果数据库同步失败怎么办？

**专业解释**

需要保证失败后能够识别 Redis 和数据库的状态差异，并通过重试、持久化日志、事务或恢复流程，避免计数器回退和序号重用。若 Redis 已经分配号段但数据库未持久化，不能简单把 Redis 重置为数据库旧值。

**大白话解释**

Redis 已经把数字加上去了，数据库却没记住。不能直接把 Redis 改回数据库的旧数字，否则已经发出去的编号可能被再次使用。

**面试表达**

> 需要区分 Redis 更新成功、数据库同步失败和业务编码是否已经对外使用这几种状态。恢复时不能直接用数据库旧值覆盖 Redis，而应根据已分配号段和业务使用记录恢复到不小于已发放序号的安全位置。具体采用事务、重试还是补偿机制，需要看项目实现。

### Q11：为什么一次生成 50 个编号？这有什么并发意义？

**专业解释**

批量生成可以减少重复的初始化、数据库访问或锁竞争，但批次大小会影响锁持有时间、吞吐量和故障时的空号范围。若一次预留 50 个号段，必须保证区间分配本身是原子的。

**大白话解释**

一次处理 50 个，可以少做很多次重复操作，但一次占用的时间也可能更长。其他请求要么等，要么在拿到独立号段后并行处理，取决于系统设计。

**面试表达**

> 业务一次可能需要批量生成 50 个安全编码。批量处理可以减少重复操作，但也要考虑锁的持有时间。如果业务要求同一编号范围的批次严格串行，就要在批次处理完成后释放锁；如果只是原子预留不同号段，则可以缩短锁的持有时间。两种方式的并发特征不同。

### Q12：唯一性和连续性有什么区别？

**专业解释**

唯一性要求编号不重复；连续性要求序号按规则递增且没有缺口。预留号段后发生故障可能产生空号，但不代表发生重复。

**大白话解释**

101、102、104 不重复，但少了 103。它满足唯一性，却不满足绝对连续。

**面试表达**

> 我会优先区分业务到底要求唯一还是严格连续。分布式批量预留和故障恢复过程中可能产生空号，但只要不重复且能够追溯，通常不影响唯一性。如果业务要求绝对连续，就需要更严格的事务和回滚设计。

**最终要真正讲透的不是“我用过 Redis 锁”，而是：为什么会发生重复、锁保护了什么、计数器如何递增、数据库如何保存，以及系统故障后怎样避免重新发放已经使用过的编号。**
