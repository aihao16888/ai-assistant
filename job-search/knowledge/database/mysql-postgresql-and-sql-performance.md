## 1. 一句话结论

数据库能力不只是会写 SQL，而是要理解数据如何组织、索引如何工作、事务如何保证一致性，以及如何通过执行计划定位查询慢的原因。

## 2. 数据库在后端系统中承担什么职责？

**专业解释：** 关系型数据库负责持久化结构化数据，并通过事务、约束、索引、并发控制和查询优化器，为业务系统提供数据管理能力。

**大白话：** Java 服务负责处理业务规则，数据库负责把业务数据可靠地保存下来，并且让多个请求同时读写时尽量保持正确。

数据库不会自动理解所有业务规则。比如“某个安全编码全局唯一”，如果系统没有正确的唯一约束或并发分配机制，不能指望数据库仅凭存储数据就自动避免重复。

## 3. 索引是什么？

### 3.1 专业解释

索引是数据库为提高检索效率建立的辅助数据结构。MySQL InnoDB 和 PostgreSQL 的常见 B-tree 索引都能帮助数据库快速定位满足条件的记录，减少不必要的数据页扫描。

### 3.2 大白话

没有索引时，数据库可能要一行一行地检查数据；有合适索引时，可以先通过索引找到目标位置，再读取对应记录。索引类似书的目录，但目录本身也需要维护。

### 3.3 常见索引考点

- **选择性（Selectivity）**：字段值越能区分记录，通常越适合用于高效过滤。
- **联合索引**：多个字段组成一个索引，字段顺序影响可使用的查询前缀。
- **最左前缀**：MySQL InnoDB 的联合 B-tree 索引通常可利用从最左列开始的连续前缀；PostgreSQL 的多列 B-tree 也受前导列约束，但优化规则并非一句“只能最左前缀”就能概括。
- **覆盖索引**：查询所需字段都能从索引中取得，可减少回表或访问堆表的成本；MySQL 和 PostgreSQL 的实现细节不同。
- **索引维护成本**：索引会占用空间，并增加 INSERT、UPDATE、DELETE 的维护成本。

### 3.4 可能导致索引效果不佳的情况

- 在索引列上执行函数或计算，导致条件难以直接利用索引；
- 对索引列进行不必要的类型转换；
- 使用前置通配符的模糊匹配；
- 联合索引字段顺序与查询条件不匹配；
- 查询返回大量记录，优化器判断扫描表更划算；
- 统计信息过期或数据分布特殊。

这些情况不是机械规则，最终应通过执行计划确认。

## 4. DMS 案例：数据库 Long 与 Java String 类型不一致

### 4.1 已知现象

用户描述：编号相关表中的组件 ID 在数据库中是 Long/数值类型，Java 对象中曾定义为 String。查询时出现非预期的查询行为；把 Java 参数调整为 Long 后，查询变成预期的等值查询。

### 4.2 专业解释

Java 实体字段类型、MyBatis/JDBC 参数类型和数据库列类型应该保持一致。类型不一致可能引发隐式转换、显式 CAST 或不同的参数绑定行为，从而影响比较语义和执行计划。

例如，数值列使用字符串参数比较时，数据库可能需要转换参数，也可能因为 SQL 写法、驱动绑定类型或数据库方言而对列进行转换。若转换作用于索引列，可能降低索引使用效率。但不同数据库和不同 SQL 写法的行为并不相同，不能直接断言“String 一定全表扫描”。

### 4.3 大白话解释

数据库里存的是数字，Java 却把它当成字符串传过去。数据库在比较时可能需要先做类型转换。如果转换方式让原本能直接使用的索引条件变复杂，就可能查得更慢。

最稳妥的方式是让 Java 属性类型、SQL 参数类型和数据库列类型保持一致，而不是让数据库每次查询都猜测如何转换。

### 4.4 正确排查步骤

1. 查看表结构，确认列类型和索引。
2. 查看 Java 实体属性类型。
3. 查看 MyBatis Mapper 或 JDBC 参数绑定方式。
4. 打印最终 SQL 和参数类型，不只看 SQL 文本。
5. 在相同数据条件下分别执行 EXPLAIN。
6. 比较是否使用索引、扫描行数、过滤条件和实际耗时。
7. 修改类型映射后重新执行计划和回归测试。

## 5. SQL 调优的系统方法

### 第一步：先确认问题

区分是 SQL 执行慢、数据库连接池等待、锁等待、网络耗时，还是应用层处理慢。不能看到接口慢就直接加索引。

### 第二步：获取执行计划

- MySQL：使用 EXPLAIN；在支持的版本中可使用 EXPLAIN ANALYZE 查看实际执行信息。
- PostgreSQL：使用 EXPLAIN；需要观察实际执行时可使用 EXPLAIN ANALYZE，并注意它会真实执行语句。对写操作尤其要谨慎。

重点关注：
- 扫描方式；
- 估算行数与实际行数；
- 使用的索引；
- Join 类型和顺序；
- Sort、Aggregate；
- 过滤后剩余行数；
- 是否出现大量回表、临时排序或磁盘操作。

### 第三步：检查索引与查询条件

- WHERE 条件是否能利用索引；
- JOIN 两侧字段类型是否一致；
- 是否有不必要的 SELECT *；
- 分页是否使用大 OFFSET；
- 是否需要联合索引；
- 是否出现 N+1 查询；
- 查询是否可以通过批量读取或减少往返优化。

### 第四步：再考虑结构与业务方案

如果 SQL 本身合理但访问量很大，可以考虑缓存、读写分离、异步化、分区或数据归档等方案。它们会增加系统复杂度，必须先确认瓶颈。

## 6. 事务与 ACID

### 6.1 ACID

- **Atomicity 原子性**：事务内操作要么全部成功，要么全部回滚。
- **Consistency 一致性**：事务前后必须满足数据库约束和业务不变量。
- **Isolation 隔离性**：并发事务之间按隔离级别限制彼此可见的中间状态。
- **Durability 持久性**：事务提交后，数据在系统承诺的故障模型内能够持久保存。

大白话：一次业务操作如果包含多条 SQL，要么一起成功，要么按事务规则一起失败；并发执行时不能随便读到别人尚未提交的中间状态；提交成功后不能轻易丢失。

### 6.2 常见隔离问题

- **脏读**：读取了其他事务尚未提交的数据。
- **不可重复读**：同一事务内多次读取同一行，结果发生变化。
- **幻读**：同一事务内重复执行范围查询，返回的记录集合发生变化。

MySQL InnoDB 与 PostgreSQL 的 MVCC、默认隔离级别和锁行为有差异，不能把一种数据库的实现细节直接套到另一种数据库上。

### 6.3 MySQL 与 PostgreSQL 的初步比较

| 维度 | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 并发控制 | MVCC 与行锁等机制 | MVCC 与多版本元组机制 |
| 默认隔离级别 | 通常为 REPEATABLE READ | 通常为 READ COMMITTED |
| 主键/索引组织 | InnoDB 主键是聚簇索引，二级索引包含主键值 | 表数据与索引分离，常见索引访问后需要访问堆表 |
| 执行计划 | EXPLAIN / EXPLAIN ANALYZE（依版本） | EXPLAIN / EXPLAIN ANALYZE |
| 类型系统 | 提供多种数值、字符、日期类型 | 类型系统较丰富，类型转换和参数类型需要明确 |

以上是初步概念对比，实际行为还受版本、配置、SQL 和索引设计影响。

## 7. 面试回答示例

**问：你遇到过什么数据库查询问题？**

答：我们有一张编号相关表，数据库字段是数值类型，但 Java 对象曾经把对应 ID 定义成 String。后来排查发现参数类型与列类型不一致会影响查询行为，将 Java 属性调整为 Long 后，查询恢复到预期的等值匹配。这个问题让我意识到 SQL 调优不能只看 SQL 文本，还要同时检查实体类型、参数绑定、字段索引和执行计划。具体是否因为隐式转换导致索引没有使用，需要结合当时的 SQL 和 EXPLAIN 证据确认。
