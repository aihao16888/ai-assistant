# 多实例部署与分布式系统：从单机到跨服务故障排查

> 优先级：P0 必须掌握  
> 掌握状态：待测评；目标 S3  
> 关联项目：DMS 多服务器部署、Redis 分布式锁、共享数据库、OA 与第三方系统集成。

## 先区分三个概念

- **多台服务器**：基础设施层有多台机器。
- **多实例部署**：同一个应用运行多个独立进程。
- **微服务架构**：按业务能力拆分成多个可独立部署和演进的服务。

三台服务器不自动等于微服务，也不自动意味着高可用。

## 1. 为什么应用要部署多个实例？

~~~text
用户请求
   ↓
负载均衡入口
   ├── 应用实例 A
   ├── 应用实例 B
   └── 应用实例 C
           ↓
      共享数据库
~~~

多个实例可以分担请求、横向扩展和在单个实例故障时继续提供服务。

但要注意：如果所有应用实例共用一个单点数据库，数据库故障仍可能让整个业务不可用。高可用必须看完整链路，而不是只看应用服务器数量。

## 2. 多实例会引入哪些单机环境没有的问题？

### 2.1 本地内存不共享

实例 A 在内存中保存的对象，实例 B 看不到。

如果登录状态、验证码、任务状态或业务计数只放在本地内存，用户下一次请求被分配到另一个实例时，可能找不到之前的数据。

常见处理：

- Session 采用共享存储或无状态 Token；
- 临时共享状态放到 Redis 或数据库；
- 文件放到共享对象存储或共享文件系统；
- 不把本地内存当作跨实例事实来源。

### 2.2 本地锁不跨 JVM

实例 A 的 synchronized 不会让实例 B 等待。

跨实例竞争同一资源时，需要共享协调机制，例如数据库锁、Redis 分布式锁或原子更新。

但最终数据约束仍应落在数据库或权威存储中，不能只依赖锁。

### 2.3 定时任务可能执行多次

如果三个实例都运行同一个定时任务，可能每个实例都执行一遍。

解决思路取决于业务：

- 任务本身设计成幂等；
- 使用数据库任务状态或唯一约束；
- 使用分布式调度或租约；
- 对任务分片并记录执行状态。

不能因为“应用只有一份代码”就认为任务只会执行一次。

## 3. 多个应用实例如何访问同一数据库？

每个应用实例通常有自己的数据库连接池，但它们连接到同一个数据库服务或集群。

数据库统一处理事务、索引、约束和并发访问。

所以：

- 请求落到哪台应用机器，不决定数据保存在哪台应用机器；
- 多个实例更新同一行，仍可能发生锁等待和并发冲突；
- 数据库连接池需要按实例数量整体估算，不能只看单个实例；
- 数据库本身可能成为连接数、CPU、IO 或锁竞争瓶颈。

## 4. 同步调用为什么会发生级联故障？

假设 A 同步调用 B，B 又同步调用 C：

~~~text
请求 A
  ↓ 等待
服务 B
  ↓ 等待
服务 C
~~~

如果 C 变慢，B 的线程会被占住，A 也在等待。请求量上升后，线程池和连接池可能逐步耗尽。

必须掌握：

- **Timeout**：调用最多等待多久，避免无限等待；
- **Retry**：哪些错误值得重试，重试几次，间隔多久；
- **Idempotency**：重试会不会重复产生副作用；
- **Circuit Breaker**：依赖持续失败时暂时停止调用，避免故障扩散；
- **Bulkhead**：隔离不同依赖或任务的资源，避免互相拖垮。

重试不是越多越好。下游已经过载时继续重试，可能把局部故障放大成整体故障。

## 5. 同步调用和异步消息怎么选择？

| 方式 | 适合场景 | 主要风险 |
|---|---|---|
| HTTP / RPC 同步调用 | 当前请求必须立即拿到结果 | 超时、级联故障、重试重复副作用 |
| RabbitMQ 等异步消息 | 后续处理可以异步完成，生产消费需要解耦 | 重复投递、消息积压、顺序和最终一致性 |

选择标准不是“哪个更先进”，而是业务是否必须等待结果、失败后如何恢复、能否接受最终一致性。

## 6. 跨服务的数据为什么容易不一致？

假设 DMS 更新自己的审批状态，还需要通知第三方系统：

~~~text
DMS 数据库更新成功
    ↓
调用第三方失败
    ↓
DMS 已经是新状态，第三方仍是旧状态
~~~

这是跨系统一致性问题。单个数据库事务不能自动覆盖另一个系统的数据库或 HTTP 接口。

常见处理：

1. 记录待同步状态；
2. 使用消息队列异步发送；
3. 采用 Outbox 减少数据库与消息双写窗口；
4. 使用稳定业务事件 ID 做幂等；
5. 对失败事件有限重试；
6. 超过重试上限进入人工或自动补偿；
7. 通过对账任务发现长期不一致。

这类设计通常追求可恢复的最终一致性，而不是假设所有系统同时成功。

## 7. 线上如何排查跨实例问题？

遇到“有时成功、有时失败”“重复执行”“只在某台机器发生”等问题：

1. 先确定请求 ID、业务 ID、发生时间和实例标识。
2. 对比不同实例的应用日志和配置。
3. 检查负载均衡、健康检查和实例是否频繁重启。
4. 检查数据库连接池、锁等待和事务状态。
5. 检查 Redis Key、过期时间和分布式锁状态。
6. 检查 MQ Ready、Unacked、重试和死信。
7. 检查第三方调用超时、响应和幂等记录。
8. 形成一条跨服务时间线，确定请求在哪个环节中断。

不要只看单台服务器的日志。跨实例排查需要统一请求标识和时间线。

## 8. DMS 三台服务器：现在能说什么，不能说什么？

已知：用户提到系统涉及三台服务器。

目前不能确认：

- 三台机器是否运行同一个 Spring Boot 服务的三个副本；
- 是否有 Nginx 或负载均衡；
- 数据库是单机、主从还是集群；
- Redis 和 RabbitMQ 的部署位置；
- 是否存在共享 Session、共享文件存储；
- 是否有服务注册发现或容器编排。

因此面试中不能直接说“我们采用了三节点微服务架构”或“实现了高可用”。先拿到脱敏部署拓扑，再确定准确表达。

## 9. 必须掌握与重点理解

### P0 必须掌握

- 多实例部署与微服务的区别；
- 负载均衡、健康检查和横向扩展；
- 多实例共享数据库时的连接池和并发问题；
- 本地内存、本地锁为什么不跨实例；
- Timeout、Retry、Idempotency 的关系；
- 同步调用与异步消息的适用场景；
- 跨系统失败后的状态记录、重试和补偿。

### P1 重点理解

- 服务注册发现、API Gateway；
- 熔断、限流、隔离和分布式追踪；
- Outbox、Saga 和最终一致性；
- 服务数据所有权和微服务边界；
- 多实例文件存储、Session 和定时任务治理。

## 10. 实操验收

1. 画出一个三实例共享数据库的部署图，标明请求入口、连接池和数据存储。
2. 模拟两个实例同时处理同一业务请求，说明本地锁为什么无效，以及如何保护数据库最终状态。
3. 模拟服务 B 超时，分析 A 是否重试、是否可能重复副作用、如何设置超时和熔断。
4. 模拟 DMS 数据库已提交但第三方同步失败，设计待同步状态、重试和对账流程。

达标标准：能区分多实例和微服务，能解释跨实例问题的来源，并能画出故障链路和恢复方案。
