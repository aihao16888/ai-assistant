# RabbitMQ：从消息发送到可靠消费，再到故障排查

> 优先级：P0 必须掌握  
> 掌握状态：待测评；目标 S3  
> 关联项目：DMS 接收 OA 审批节点消息，并按业务条件向第三方同步数据。

## 先看业务链路

~~~text
OA 审批流程推进
    ↓
产生审批节点事件
    ↓
生产者向 RabbitMQ 发布消息
    ↓
Exchange 根据 Binding 和 Routing Key 路由
    ↓
消息进入 Queue
    ↓
DMS Consumer 获取消息
    ↓
识别流程实例、业务标识和审批节点
    ↓
判断是否需要向第三方同步
    ↓
业务处理成功后 ACK
~~~

这条链路中的真实生产者、Exchange、Queue、Routing Key 和 ACK 配置仍需项目代码确认。下面解释的是 RabbitMQ 通用机制。

## 1. 为什么系统要使用消息队列？

如果 OA 每推进一个审批节点都同步等待 DMS 完成全部处理：

- DMS 响应慢会拖长 OA 请求；
- DMS 暂时不可用会影响 OA；
- 双方发布和扩容相互依赖；
- 高峰流量可能直接冲击 DMS。

消息队列让生产者先发布事件，消费者之后处理，起到异步解耦和缓冲作用。

但 MQ 不是“用了就可靠”。消息发布、路由、持久化、消费确认和业务落库，每一段都可能失败。

## 2. RabbitMQ 的核心组件是什么？

| 组件 | 做什么 | 关键问题 |
|---|---|---|
| Producer | 发布消息 | 消息是否真的到达 Broker？ |
| Exchange | 接收消息并负责路由 | 消息按什么规则分发？ |
| Binding | 建立 Exchange 到 Queue 的路由关系 | 队列是否正确绑定？ |
| Routing Key | 发布消息时携带的路由标识 | 是否匹配 Binding？ |
| Queue | 保存等待消费的消息 | 队列是否持久化、是否堆积？ |
| Consumer | 获取并处理消息 | 成功后何时 ACK？失败如何处理？ |

常见 Exchange：

- Direct：Routing Key 精确匹配；
- Topic：按带通配符的模式匹配；
- Fanout：向所有绑定队列广播；
- Headers：根据消息头匹配。

必须能从 Producer 画到 Consumer，不能只背出六个名词。

## 3. 消息如何做到尽量不丢？

可靠性至少分两端。

### 3.1 生产者到 Broker：Publisher Confirm

Publisher Confirm 用于让生产者知道 Broker 是否确认接收了发布。

它解决的是“生产者发出去的消息，Broker 有没有确认接收”的问题。

但 Confirm 不等于消费者已经处理成功。

还要考虑消息是否成功路由到队列。对于需要确保路由的消息，要结合 mandatory/Return 等机制处理不可路由消息。

### 3.2 Broker 存储：队列和消息持久化

队列持久化和消息持久化是两个不同配置维度。持久化配置能增强 Broker 重启后的恢复能力，但不代表所有故障场景下绝对不丢。

对关键业务，还要根据 RabbitMQ 版本和部署形态评估队列类型、复制和故障恢复策略。

### 3.3 Broker 到消费者：Consumer ACK

手动 ACK 模式下，消费者应在业务处理成功后确认消息。

两种错误顺序：

- 先 ACK，再写数据库：消费者在 ACK 后宕机，业务数据可能没落库，但消息已被确认。
- 先写数据库，再 ACK：如果数据库提交后 ACK 前宕机，消息可能重新投递，业务就可能重复执行。

所以可靠消费必须同时考虑 ACK 时机和业务幂等。

## 4. 为什么消费者必须考虑重复消息？

例如：

~~~text
DMS 收到消息
    ↓
数据库业务处理成功并提交
    ↓
消费者还没来得及 ACK 就宕机
    ↓
RabbitMQ 重新投递消息
    ↓
DMS 再次收到同一消息
~~~

如果第二次仍然执行相同副作用，可能重复创建记录、重复调用第三方或重复推进业务状态。

解决办法是建立稳定的业务幂等键，例如：

- 消息 ID；
- 流程实例 ID + 节点 ID；
- 业务单号 + 事件版本。

在数据库事务内检查和记录该事件是否已经处理。重复消息如果确认属于已处理事件，可以不再执行副作用，并正常 ACK。

**不要把“RabbitMQ 只投递一次”当成可靠性设计。** 实际业务通常应按可能重复投递来设计消费者。

## 5. 失败重试与死信队列

消费者可能遇到：

- 第三方接口短暂超时；
- 数据库连接暂时失败；
- 消息字段不合法；
- 业务状态不允许处理；
- 依赖服务持续不可用。

处理策略要区分错误类型：

| 失败类型 | 建议处理 |
|---|---|
| 短暂网络或依赖故障 | 有次数上限的延迟重试 |
| 参数或消息格式错误 | 不要无限重试，进入死信或人工处理 |
| 业务状态暂不满足 | 根据业务设计延迟重试或记录待处理状态 |
| 第三方持续不可用 | 限流、退避重试、告警和补偿 |

无限立即重试会造成热循环，持续占用消费者和 Broker 资源。

死信队列（DLQ）用于接收达到死信条件的消息，便于排查和后续处理。进入 DLQ 不代表问题自动解决，必须有告警、查询和人工/自动补偿流程。

## 6. Prefetch 为什么重要？

Prefetch 限制消费者在未 ACK 状态下可以同时持有多少条消息。

- 太大：消费者可能积压大量未确认消息，增加内存和恢复压力；
- 太小：消费者并发不足，处理能力可能无法充分利用；
- 设置为 0：表示不限制未确认消息数量，需谨慎。

要结合单条消息处理耗时、消费者数量、机器资源和下游数据库能力调整。

## 7. 数据库更新与消息发布为什么会不一致？

例如 DMS 更新审批状态后，还要发布“审批已通过”事件：

~~~text
先更新数据库，再发消息
  → 数据库成功，消息发布失败

先发消息，再更新数据库
  → 消息已被消费，数据库事务却回滚
~~~

Transactional Outbox 是常见方案：在同一个数据库事务中写业务数据和待发布事件记录，再由后台发布器把事件可靠发送到 MQ。

它减少数据库和 MQ 双写之间的不一致窗口，但需要处理 Outbox 重复发布、状态更新和消费幂等。

**这是通用方案，不代表 DMS 当前已经实现 Outbox。**

## 8. 消息堆积怎么排查？

先区分两种队列状态：

- Ready：在队列中等待投递的消息；
- Unacked：已经投递给消费者但尚未确认的消息。

排查顺序：

1. 查看 Ready 是否持续增长；
2. 查看 Unacked 是否异常增加；
3. 查看消费者数量和消费者是否在线；
4. 检查消费者处理耗时、错误率和线程池；
5. 检查 Prefetch 和 ACK 是否正常；
6. 检查下游数据库、第三方接口是否变慢；
7. 查看是否有大量重试或死信；
8. 找出最早积压时间和异常消息样本。

常见判断：

- Ready 高、Unacked 低：消费者数量不足、消费速度慢或消息没有正常投递；
- Unacked 高：消费者拿到消息但处理慢、阻塞或没有 ACK；
- 队列反复增长：生产速度长期超过消费能力，或消费者持续失败。

## 9. DMS 项目映射

已知业务描述：OA 审批流程推进时产生节点相关消息，消息同步到 DMS；DMS 根据当前节点和业务状态判断是否需要向第三方同步。

仍需核实：

- [ ] 实际消息生产者是谁；
- [ ] OA 是否直接发 RabbitMQ，还是经过中间服务；
- [ ] Exchange、Queue、Binding 和 Routing Key；
- [ ] DMS 的消费者代码和消息字段；
- [ ] ACK 是自动还是手动；
- [ ] Publisher Confirm 和不可路由消息处理；
- [ ] 重试次数、延迟策略和死信队列；
- [ ] 第三方接口是否有幂等键；
- [ ] 数据库更新与消息发布之间如何保证一致性。

不能在未检查代码和配置前，声称项目已经具备消息不丢、恰好一次或自动补偿能力。

## 10. 必须掌握与重点理解

### P0 必须掌握

- Producer、Exchange、Binding、Routing Key、Queue、Consumer；
- Direct、Topic、Fanout 的基本路由区别；
- Publisher Confirm 与 Consumer ACK 的区别；
- 手动 ACK 的正确时机；
- 为什么消息会重复投递；
- 消费幂等如何实现；
- 重试、死信和消息积压的排查方法；
- 第三方调用失败后的状态记录和补偿思路。

### P1 重点理解

- 持久化、复制队列和故障恢复；
- Prefetch、消费者并发和吞吐量；
- 消息顺序与多消费者；
- Outbox 和最终一致性；
- 延迟重试、死信治理和人工重放。

## 11. 实操验收

1. 创建一个 Direct Exchange、Queue 和 Binding，验证 Routing Key 是否路由成功。
2. 写一个手动 ACK 消费者，分别模拟处理成功、处理异常和 ACK 前宕机。
3. 让消费者在数据库提交后、ACK 前中断，观察重复投递并实现幂等。
4. 制造消费者处理慢的情况，观察 Ready、Unacked 和 Prefetch 的变化。

达标标准：能画出消息生命周期，解释每个确认点保护什么，能处理重复、失败和积压。
