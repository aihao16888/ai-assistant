# Java 并发：从线程安全到线程池排查

> 优先级：P0 必须掌握  
> 掌握状态：待测评；目标 S3  
> 关联项目：DMS 安全编码批量生成、重复提交防护。

## 先看问题：为什么两个请求会生成同一个编号？

假设两个请求同时进入同一个 Java 服务实例：

~~~text
线程 A：读取当前序号 100
线程 B：读取当前序号 100
线程 A：计算 100 + 1，得到 101
线程 B：计算 100 + 1，得到 101
线程 A：写入 101
线程 B：写入 101
~~~

两个请求都认为自己拿到了下一个编号。问题不是 Java 算错了，而是多个线程同时执行了一个没有保护的“读取—计算—写入”过程。

这就是并发问题的核心：**多个执行单元访问共享状态时，操作顺序会影响最终结果。**

## 1. 先分清进程、线程和共享数据

- **进程**：操作系统运行程序时的资源隔离单位。一个 Java 服务通常运行在一个 JVM 进程中。
- **线程**：进程内的执行单元。一个服务可同时使用多个线程处理请求。
- **共享数据**：多个线程都能访问的对象或变量，例如堆中的对象、缓存、计数器。

同一个 JVM 进程里的线程可以共享堆对象；不同 JVM 进程拥有各自的内存空间。

因此，Java 本地锁只能协调当前 JVM 里的线程，不能自动协调其他服务器上的 JVM。

## 2. 并发问题必须掌握的三个概念

### 2.1 原子性

一个操作是否不可分割。

count++ 看起来是一行代码，实际包含读取、计算、写回多个步骤。多个线程同时执行时可能互相覆盖，所以它不是天然的原子操作。

### 2.2 可见性

一个线程修改了共享变量，其他线程是否能按 Java 内存模型规定看到这个修改。

如果没有正确同步，线程可能读到旧值，不能简单依赖“另一个线程已经改过了”。

### 2.3 有序性

编译器和处理器可能在不改变单线程语义的前提下调整指令顺序。多线程之间需要通过同步关系建立必要的先后约束。

这三者属于 Java 内存模型（JMM）要解决的问题。实际开发中不必先背抽象定义，先判断：共享变量有没有被多个线程访问？读写之间有没有正确同步？

## 3. 四种常用工具分别解决什么问题？

| 工具 | 主要用途 | 不能误认为 |
|---|---|---|
| synchronized | 对临界区互斥，并建立可见性关系 | 不能跨 JVM |
| ReentrantLock | 显式互斥，支持超时、可中断、公平性和多个 Condition | 不会自动释放，需 finally unlock |
| volatile | 保证变量读写的可见性并约束相关重排序 | 不能让 count++ 变成原子操作 |
| AtomicInteger / AtomicLong | 对单个变量执行原子更新，常通过 CAS 实现 | 不能自动保护多个变量组成的业务事务 |

### 3.1 synchronized

~~~java
synchronized (lock) {
    // 访问或更新共享状态
}
~~~

进入同步块需要获得同一个监视器；退出时释放。适合简单的互斥区域。

### 3.2 ReentrantLock

~~~java
lock.lock();
try {
    // 访问共享状态
} finally {
    lock.unlock();
}
~~~

当业务需要 tryLock、超时等待、可中断获取或多个条件队列时，可以考虑它。使用显式锁时必须保证异常路径也能释放。

### 3.3 volatile

适合状态标记，例如线程停止标志：

~~~java
private volatile boolean running = true;
~~~

一个线程把 running 改为 false，其他线程能够按 volatile 语义观察到更新。但如果要执行“检查余额再扣款”这样的复合操作，volatile 不够。

### 3.4 AtomicInteger

~~~java
AtomicInteger counter = new AtomicInteger(100);
int next = counter.incrementAndGet();
~~~

对单个计数器递增是原子操作。如果业务流程包含“检查序列范围—分配一段号码—更新多个状态”，不能只因为使用了 AtomicInteger 就认为整条流程安全。

## 4. 本地锁为什么解决不了多台服务器的问题？

~~~text
请求 A → 应用实例 1 → JVM 1 的锁
请求 B → 应用实例 2 → JVM 2 的锁
请求 C → 应用实例 3 → JVM 3 的锁
~~~

三个 JVM 各有自己的锁对象。JVM 1 加锁，不会让 JVM 2 自动等待。

跨实例协调需要所有实例都能访问的共享机制，例如：

- 数据库行锁或原子更新；
- Redis 分布式锁；
- 专门的协调服务。

具体选择取决于业务要求。分布式锁也不是最终数据正确性的唯一保障，关键数据仍应有数据库约束或原子更新保护。

## 5. 线程池为什么是后端必须掌握的内容？

如果每个请求都创建新线程，流量高时线程数量可能失控，线程创建和切换也有成本。线程池复用线程，并限制并发任务数量。

ThreadPoolExecutor 的任务处理顺序：

1. 当前线程数少于 corePoolSize：优先创建核心线程。
2. 核心线程达到上限：新任务进入工作队列。
3. 队列满了：如果线程数还没达到 maximumPoolSize，则继续创建非核心线程。
4. 线程数达到最大值且队列已满：执行拒绝策略。

必须理解的参数：

- corePoolSize：核心线程数；
- maximumPoolSize：最大线程数；
- keepAliveTime：非核心线程空闲多久后回收；
- workQueue：等待执行的任务队列；
- RejectedExecutionHandler：任务无法接收时如何处理。

**常见故障：** 线程池队列无界增长，任务迟迟不执行，内存持续上升；或者线程池耗尽，后续请求被拒绝。

排查时看：活跃线程数、队列长度、任务等待时间、拒绝次数、任务执行耗时和线程栈。

## 6. 死锁是怎么发生的？

~~~text
线程 A：持有锁 1，等待锁 2
线程 B：持有锁 2，等待锁 1
~~~

双方都无法继续。

常见预防方法：

- 多把锁按固定顺序获取；
- 缩短临界区；
- 避免持锁期间调用远程服务；
- 必要时设置超时；
- 分析线程转储中的锁持有和等待关系。

## 7. 线上如何排查并发问题？

### 线程阻塞或接口一直不返回

1. 确认接口、实例、请求 ID 和发生时间。
2. 检查线程池是否满、队列是否持续增长。
3. 获取线程转储，观察大量线程处于 BLOCKED、WAITING 还是 RUNNABLE。
4. 查找锁持有者、等待链和是否存在死锁。
5. 对照业务日志确认线程卡在哪一步。

Linux / JVM 常用命令：

~~~bash
jps -l
jstack <pid> > thread-dump.txt
top -H -p <pid>
~~~

不要只凭线程状态下结论。要结合多份线程转储、CPU 使用率、日志和请求时间线。

### CPU 突然很高

- 用 top -H -p 找到高 CPU 线程；
- 结合线程转储定位执行栈；
- 检查死循环、忙等、频繁 GC 或过高并发；
- 修复后对比 CPU、请求耗时和错误率。

## 8. DMS 项目映射

已知：安全编码由后台生成，一次请求可能批量生成约 20–50 个编号；多个请求可能竞争同一序号范围；项目使用 Java 本地锁和 Redis 分布式锁。

可以确认的知识映射：

- Java 本地锁：协调同一 JVM 内的线程；
- Redis 分布式锁：用于跨实例协调；
- 锁粒度：必须和业务序号共享范围一致。

仍待核实：本地锁类型、锁 Key、锁的获取和释放位置、锁过期策略、异常路径，以及数据库是否有唯一约束。
