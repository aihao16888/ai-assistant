# Redis：从防重到分布式锁，再到原子计数

> 优先级：P0 必须掌握  
> 掌握状态：待测评；目标 S3  
> 关联项目：DMS 受控发布防重、安全编码生成。

## 先把三个用途分开

当前 DMS 资料中，Redis 主要涉及三类任务：

| 用途 | 解决的问题 | 不能替代什么 |
|---|---|---|
| 防重 | 短时间内拦截相同提交 | 不能单独保证完整业务幂等 |
| 分布式锁 | 多个应用实例协调进入临界区 | 不能单独保证数据库最终唯一 |
| 原子计数 | 多客户端安全地领取递增值 | 不能自动解决 Redis 与数据库的数据恢复 |

如果先把这三个概念分清，后面的机制就容易理解。

## 1. Redis 为什么常用于这些场景？

Redis 是一个以内存数据结构为核心的共享服务，支持 String、Hash、Set、List 等结构，以及原子命令和过期时间。

多个应用实例都能访问同一 Redis 服务，因此它可以承担共享状态和快速协调的角色。

但 Redis 不是数据库的通用替代品。业务最终数据、关系约束和持久化正确性仍需明确由谁负责。

## 2. 场景一：如何防止同一请求短时间重复提交？

### 问题

用户对同一份文件连续点击提交，两个请求几乎同时到达服务端。

错误写法：

~~~text
请求 A：GET key → 不存在
请求 B：GET key → 不存在
请求 A：SET key
请求 B：SET key
两个请求都继续提交
~~~

“先检查、后写入”是两个独立动作，中间存在并发窗口。

### 正确思路：原子占位

~~~text
SET dms:publish:dedup:<business-id> <request-token> NX EX 60
~~~

- NX：仅当 Key 不存在时写入；
- EX：设置过期时间；
- 返回成功：当前请求获得短期占位资格；
- 返回未设置：Key 已存在，当前请求可被识别为重复提交。

检查和写入由一条 Redis 命令完成，避免两个请求都通过“先检查”。

### 防重不等于幂等

防重主要拦截重复请求；幂等要求同一个业务操作执行多次，最终业务结果仍等价于执行一次。

例如第一次请求已成功写入数据库，但响应在网络中丢失，用户重试时，Redis Key 可能已过期或丢失。仅靠短期 Key 不足以保护业务结果。

完整设计还需要：

1. 稳定的业务幂等标识；
2. 数据库业务状态校验；
3. 必要时使用唯一约束；
4. 明确处理中、成功、失败等状态；
5. 对失败后的重试、释放和补偿作出规定。

**DMS 已知事实：** 使用 Redis 拦截短时间重复受控发布。实际是否使用 SET NX、Key 维度、TTL 和失败补偿待代码核实。

## 3. 场景二：为什么需要分布式锁？

Java synchronized 或 ReentrantLock 只能协调同一个 JVM 进程内的线程。

如果三个应用实例同时申请同一个编号范围，它们各自的本地锁互相不可见。

因此需要共享协调点，让多个实例竞争同一把逻辑锁。

### 基础机制

~~~text
SET lock:<sequence-scope> <unique-token> NX PX 30000
~~~

- Key：要保护的业务资源或序号范围；
- Token：当前持有者唯一标识；
- NX：只有 Key 不存在才能获得锁；
- PX：设置毫秒级租约，避免进程宕机后永久占锁。

获得锁后才能执行临界区；未获得锁的请求应等待、重试或返回繁忙。

### 为什么释放锁不能直接 DEL？

假设：

1. A 获得锁；
2. A 执行太久，锁过期；
3. B 获得同一个 Key；
4. A 恢复执行并直接 DEL；
5. A 删除了 B 的锁。

因此释放锁必须原子地比较 Token，只有当前 Key 仍属于自己才删除，通常通过 Lua 脚本完成比较和删除。

### 锁过期后，旧线程还在运行怎么办？

这是分布式锁最重要的边界：

~~~text
A 获得锁
  ↓
A 执行超过 TTL
  ↓
锁过期，B 获得锁
  ↓
A 仍在执行
  ↓
A、B 可能同时修改业务数据
~~~

锁过期并不会自动停止旧线程。需要根据业务关键程度考虑：

- 合理设置 TTL；
- 必要时续期；
- 释放时校验 Token；
- 通过数据库条件更新或唯一约束保护最终结果；
- 对严格防止旧持有者写入的场景，考虑 fencing token（栅栏令牌）。

fencing token 必须由系统实际生成并由下游存储校验，普通 Redis 锁不会自动提供这项保护。

**记住：分布式锁是并发协调工具，不是数据正确性的最终证明。**

## 4. 场景三：Redis INCR 为什么能安全递增？

假设序号当前为 100，多个客户端同时领取下一个序号。

错误方式：

~~~text
GET key → 100
Java + 1 → 101
SET key 101
~~~

多个客户端可能都读到 100，最后都写入 101。

Redis 的 INCR 是服务端原子命令：

~~~text
INCR sequence:car:202611
~~~

同一个 Key 的多个 INCR 命令不会因为客户端都读取相同旧值而互相覆盖，返回值会依次递增。

批量分配可以考虑 INCRBY 一次预留一段区间，例如当前 100，执行 INCRBY key 50，得到 150，则按业务规则分配 101–150。

但批量预留可能出现跳号：预留成功后应用宕机，未使用的号码可能不会回收。是否允许跳号必须由业务规则决定，不能只从技术角度决定。

### 四种机制不要混淆

- Java 本地锁：保护当前 JVM 内的临界区；
- Redis 分布式锁：协调多个客户端进入一段临界区；
- Redis INCR/INCRBY：保证单个计数操作原子执行；
- 数据库唯一约束：最终拒绝重复业务值。

## 5. Redis 与数据库不同步，会出现什么风险？

假设 Redis 保存最新序号，数据库序号表保存持久化状态：

~~~text
Redis 当前序号 150
  ↓
应用已经发放 101–150
  ↓
最新序号尚未写回数据库
  ↓
应用或 Redis 发生故障
  ↓
Redis 数据丢失，数据库仍记录 100
  ↓
恢复后可能重新分配已发放过的序号
~~~

关键问题不是“Redis 快不快”，而是：**已经对外发放的序号，是否有可靠的持久化依据？**

需要明确：

- 数据库还是 Redis 是序号权威来源？
- Redis 丢失后如何恢复？
- Redis 写成功、数据库写回失败怎么办？
- 数据库写成功、Redis 写失败怎么办？
- 是否允许跳号？
- 是否有数据库唯一约束作为最后防线？

一种可论证的方案是先在数据库事务中原子预留序号区间，再让应用分配该区间；Redis 可以承担加速和协调角色。是否适用于 DMS，要看真实业务规则和现有实现。

## 6. 线上如何排查 Redis 问题？

先确认是哪一种问题，不要一上来就重启 Redis。

### Key 或防重异常

~~~text
TYPE <key>
GET <key>
TTL <key>
PTTL <key>
~~~

确认 Key 类型、值和剩余过期时间。检查 Key 的业务维度是否正确，是否出现不同业务共用一个 Key。

### 锁一直拿不到

- 是否有锁 Key 长时间存在？
- TTL 是否正常递减？
- 持有者是否宕机？
- 是否存在续期失败？
- 释放逻辑是否 Token 不匹配？
- 锁 Key 是否过粗，导致无关业务互相等待？

### 计数器不正确

- 是否有多个不同 Key 表示同一序号范围？
- 是否出现 GET + Java 计算 + SET 的非原子逻辑？
- 是否有过期、淘汰、恢复或数据库回写失败？
- 是否允许批次失败造成跳号？
- 数据库唯一约束是否存在？

### Redis 性能异常

- 检查延迟、CPU、内存、连接数和慢命令；
- 检查是否执行了大 Key 操作或高复杂度命令；
- 慎用生产环境 MONITOR，它可能带来额外开销并暴露业务数据；
- 结合应用日志确认 Redis 等待是否是接口慢的真正原因。

## 8. 必须掌握与重点理解

### P0 必须掌握

- 缓存、防重、幂等、分布式锁、原子计数的区别；
- SET NX EX/PX 的语义；

- Redis 和数据库之间的数据恢复风险；
- 锁 Key 与业务资源范围必须一致。

### P1 重点理解

- Redis RDB/AOF、复制和故障切换；
- 缓存穿透、击穿、雪崩；
- 缓存与数据库一致性；
- Lua 脚本的原子执行边界；
- fencing token 与严格并发写保护。

## 9. 实操验收

1. 两个客户端同时执行 GET + SET，观察计数覆盖；改成 INCR 后再观察。
2. 用 SET NX PX 模拟锁获取，验证第二个客户端不能同时获得锁。
3. 模拟 A 锁过期、B 获锁、A 再释放的场景，验证 Token 校验的重要性。
4. 模拟 Redis 计数器高于数据库记录后发生数据丢失，分析如何避免重复发号。

达标标准：能解释防重、幂等、锁、计数器的区别，能说明锁失效风险，并能设计 Redis 与数据库之间的恢复策略。
