## 1. 一句话概括

参与企业文档管理系统的后端开发与维护，围绕文档受控发布、审批流转、编号生成、数据存储和第三方系统同步等业务，处理并发提交、消息异步传递、数据查询和线上问题。

这句话是当前素材的概括，不代表已经确认用户独立负责全部模块。面试最终版本必须按本人实际职责修改。

## 2. 业务背景与核心流程

DMS 用于企业文档业务管理。当前已讨论的典型业务包括：

- 文档或文件申请、评审和审批；
- 文档受控发布；
- 文档编号与安全编码生成；
- OA 审批流程与 DMS 之间的数据同步；
- 审批节点达到指定条件后，再向第三方系统同步业务数据；
- 文档相关数据的查询、维护与线上问题排查。

### 2.1 OA 审批与 DMS 同步

根据目前描述，OA 系统中的流程引擎负责审批流转。流程提案发起后，相关流程消息会同步到 DMS；流程经过审批节点时，DMS 需要识别当前节点是否属于需要处理的目标节点，再按业务要求向第三方系统同步对应数据。

初步业务链路：

~~~text
业务人员在 OA 发起流程
        ↓
OA 流程引擎推进审批
        ↓
审批节点产生流程事件/消息
        ↓
消息同步到 DMS（具体消息方向与队列配置待核实）
        ↓
DMS 识别当前审批节点及业务状态
        ↓
判断是否满足第三方同步条件
        ↓
向第三方系统同步对应业务数据
~~~

**待核实：** OA 是直接向 RabbitMQ 发布消息，还是通过其他服务转发；DMS 是直接调用第三方接口，还是再次发布消息；消息交换机、队列、路由键和消费确认方式是什么。

### 2.2 文档受控发布与重复提交防护

业务人员可能在很短时间内对同一份文件重复点击提交。系统需要识别重复请求，避免同一个文件短时间内重复发起受控发布流程。

当前描述确认使用 Redis 做重复请求拦截：提交时记录相关文件标识，后续相同请求到来时检查 Redis 中是否已有记录，命中则阻止重复提交。

初步流程：

~~~text
用户提交受控发布
      ↓
根据文件业务标识构造防重 Key
      ↓
Redis 原子判断并写入（具体命令待核实）
      ↓
Key 已存在 ──→ 识别为重复请求，拒绝或提示
      ↓
Key 不存在 ──→ 继续业务校验与流程提交
~~~

**待核实：** Redis Key 的组成、过期时间、是否使用 SET NX、是否与数据库业务状态校验结合、提交失败后是否删除 Key、用户重试如何处理。

注意：短时间防重只能减少重复点击，不能天然代替业务幂等。若请求超时后用户重试、服务重启或 Key 过期，仍需要通过业务状态或持久化唯一约束保护最终结果。

### 2.3 安全编码生成

系统后台自动生成安全编码，编码由多个字段拼接，字段之间使用连字符。当前描述包括：

- 组织代号；
- 车型代号；
- 年月；
- 递增序号（末尾序号）。

完整安全编码要求全局唯一。系统有专门的编号表记录最新序号。一次请求可能批量生成约 20–50 个编号；多个部门可能同时为相同车型相关的编号范围申请编号，因此会竞争序号分配。

当前已确认的实现描述：

- 后台负责生成，不是由用户手工协调分配；
- 使用 Java 本地锁；
- 同时使用 Redis 分布式锁；
- Redis 参与当前序号缓存和递增；
- 生成后的最新序号状态会同步到数据库序号表。

需要特别确认：序列范围是否按组织、车型、年月等字段组合确定；不同部门是否共享同一个序列命名空间；Redis Key 与数据库序号表主键是否使用相同的范围维度。

### 2.4 数据库类型映射与查询问题

曾遇到编号相关表中的字段在数据库定义为 Long/数值类型，但 Java 对象中使用 String 类型，查询时出现与预期不同的执行效果；将 Java 参数类型调整为 Long 后，查询行为变为预期的等值查询。

这个问题可以作为数据库类型映射和 SQL 性能排查案例，但不能直接断言“String 一定导致全表扫描”。需要核对：

1. 数据库字段真实类型；
2. Java 实体字段类型；
3. MyBatis/JDBC 实际绑定的参数类型；
4. 最终生成的 SQL；
5. 字段是否有索引；
6. EXPLAIN 执行计划是否使用索引；
7. 数据库是否发生隐式类型转换或对索引列应用函数。

## 4. 可以形成的五个面试故事

### 故事 A：Redis 如何防止重复受控发布

- 业务问题：同一文件短时间内被重复提交。
- 技术方向：Redis 防重 Key、原子写入、幂等性、业务状态校验。
- 面试重点：为什么需要防重、Key 如何设计、并发下如何避免两个请求同时通过、TTL 如何选择、业务失败如何恢复。
- 当前状态：真实业务已描述；具体 Redis 命令和异常分支待核实。

### 故事 B：Redis 分布式锁如何保护安全编码序号

- 业务问题：多个请求同时批量生成编号，可能竞争相同序号。
- 技术方向：Java 本地锁、Redis 分布式锁、原子计数器、数据库序号持久化。
- 面试重点：为什么本地锁不够、锁粒度、锁过期、原子递增、Redis 与数据库一致性、唯一约束兜底。
- 当前状态：业务背景已描述；实现细节待核实。

### 故事 C：RabbitMQ 如何同步 OA 审批节点

- 业务问题：OA 流程经过审批节点时，DMS 需要接收事件并在指定节点向第三方同步数据。
- 技术方向：消息队列解耦、异步消费、路由、确认、重试、幂等。
- 面试重点：为什么使用 MQ、消息如何路由、重复消费怎么办、消费失败怎么办、如何避免第三方重复接收。
- 当前状态：业务链路已描述；消息配置和可靠性实现待核实。

### 故事 D：Java 与数据库类型不一致引发的查询问题

- 业务问题：数据库数值类型字段与 Java String 参数类型不一致，查询行为异常。
- 技术方向：类型映射、参数绑定、隐式转换、索引使用、执行计划。
- 面试重点：如何定位慢 SQL、如何确认索引是否生效、为什么不应在查询时随意转换索引列。
- 当前状态：问题现象已描述；SQL 和 EXPLAIN 证据待补。

### 故事 E：Linux 日志排查线上问题

- 业务问题：线上出现异常，需要从服务器日志定位。
- 技术方向：日志检索、请求链路、异常堆栈、时间窗口、进程与资源排查。
- 面试重点：如何从用户现象定位到请求、接口、代码和依赖服务。
- 当前状态：有日志排查经历；需要补充一个真实、完整且脱敏的故障案例。

## 5. 项目介绍表达初稿

### 约 60 秒版本

我参与过企业文档管理系统的后端开发与维护。系统涉及文档受控发布、审批流转、编号生成以及与 OA 和第三方系统的数据同步。在项目中接触过 Redis 和 RabbitMQ：Redis 一方面用于同一文件短时间重复提交的拦截，另一方面参与安全编码的序号缓存、递增和分布式并发控制；RabbitMQ 用于 OA 审批节点相关消息向 DMS 同步，DMS 根据节点和业务状态判断是否需要向第三方继续同步。此外，我也处理过数据库字段类型与 Java 参数类型不一致导致的查询问题，并通过 Linux 服务器日志进行线上问题排查。

这段表达目前是素材草稿。正式使用前，需要确认每一项是否属于本人直接负责、参与开发还是协助排查。

## 7. 当前不能直接声称的内容

- 不能声称 Redis 锁失效后一定不会重复，必须确认锁续期、持久化和数据库兜底。
- 不能声称 MQ 实现了“恰好一次”投递或消费，除非有完整机制和证据。
- 不能声称三台服务器一定是三个微服务节点；它们也可能承担不同角色。
- 不能声称数据库天然保证跨服务器业务唯一；需要确认事务、唯一约束或协调机制。
- 不能声称已经完成性能优化或提升了某个百分比，除非有前后对比数据。
