## 1. 一句话概括

针对用户在很短时间内对同一文件重复点击受控发布提交的问题，使用 Redis 保存文件相关的防重标识；后续相同文件的请求命中已有标识时，拦截重复提交，避免重复触发后续流程。

## 2. 业务背景与问题

文档受控发布需要发起后续业务流程。如果用户在网络延迟、页面响应较慢或连续点击的情况下，对同一文件短时间内重复提交，系统可能重复发起受控发布。

这里要解决的不是“用户不能重复点击”这一 UI 问题，而是后端需要识别重复请求，避免重复请求进入后续业务流程。

## 3. 当前已确认的项目事实

- 同一文件可能在很短时间内被重复点击提交。
- 系统使用 Redis 记录与文件相关的标识。
- 后续提交时检查 Redis 中是否已经存在对应文件标识。
- 如果命中已有记录，则阻止该次重复受控发布提交。

## 4. 60 秒面试表达初稿

> 我们的文档管理系统有受控发布流程，实际使用中会遇到用户对同一份文件在很短时间内连续点击提交的情况。如果每次请求都直接进入业务流程，就可能重复发起受控发布。
>
> 针对这个场景，我们在提交链路中使用 Redis 做重复请求拦截。首次提交时，把与文件关联的标识记录到 Redis；后续相同文件再次提交时，先检查 Redis，命中已有标识就拦截，不再继续触发后续流程。
>
> 这个方案利用 Redis 的快速读写和多实例共享能力，让不同请求都能检查到已有的防重状态。不过，具体采用什么原子写入命令、Key 的有效期如何设置，以及首次提交失败后如何恢复，需要结合项目代码进一步确认。我不会把短时间防重直接说成完整的业务幂等保证。

## 5. 面试官可能追问什么

### Q1：为什么使用 Redis，而不是只在 Java 里用一个 Set？

**专业解释：** Java 本地集合只存在于当前 JVM，其他服务实例看不到；实例重启后数据也会丢失。Redis 是多个应用实例可以访问的共享存储，适合保存短时间内需要共享的防重状态。

**大白话：** 本机内存里的记录只对当前服务器有效，别的服务器不知道。Redis 相当于大家共用的一份记录。

**项目边界：** 当前可以说明项目使用 Redis 做防重；具体是否有多实例同时接收这类请求，需要结合部署拓扑确认。

### Q2：如果两个请求几乎同时到达，先查再写会不会都通过？

**专业解释：** 如果实现是先 GET 判断不存在，再 SET 写入，那么两个请求可能同时读到不存在，随后都继续执行。这是典型的 check-then-act 竞态。

**常见设计：** 使用 Redis 的原子“仅当 Key 不存在时写入”能力，例如 SET NX 并设置过期时间，或通过 Lua 将判断和写入放在一个原子操作中。

**重要边界：** 这是需要理解的可靠实现方式，不代表项目已经使用 SET NX 或 Lua。实际命令必须看代码确认。

### Q3：为什么防重 Key 通常需要过期时间？

**专业解释：** 如果防重标识永久存在，后续合法操作可能一直被拦截；设置 TTL 可以限定防重窗口，避免无期限占用。

**大白话：** 不能因为用户第一次提交过，就永远不让他再提交；要根据业务流程决定多长时间后允许再次操作。

**需要确认：** 项目实际 TTL、是否在流程状态结束后主动删除，以及 TTL 是否覆盖整个业务处理中窗口。

### Q4：Redis 防重是否等于业务幂等？

**专业解释：** 不等于。短时间防重主要拦截重复点击或重复请求；业务幂等要求同一业务请求重复执行时，最终业务结果仍然一致。请求超时重试、Redis Key 过期、Redis 故障或跨业务入口重复调用，都可能绕过短时间防重。

**大白话：** Redis 可以挡住一部分重复点击，但不能保证所有情况下重复请求都不会产生重复业务结果。

**后续要核实：** 是否还有数据库唯一约束、业务状态校验、流程实例唯一标识或其他幂等保护。

### Q5：首次提交失败，Redis 标识应该怎么办？

需要区分失败发生在哪个阶段：

- 业务校验失败，尚未创建流程；
- Redis 标识已写入，但流程创建失败；
- 流程已创建成功，但响应返回失败；
- 请求超时，客户端无法判断服务端是否成功。

不能简单地认为“失败就删除 Key”总是正确，因为流程可能已经创建成功，只是响应丢失。应结合业务状态、请求唯一标识和持久化记录判断如何恢复。

**项目待核实：** 当前实现如何处理这些失败分支。
