## 1. 一句话概括

排查编号查询中数据库字段为数值类型、Java 对象查询参数却定义为 String 的类型不一致问题；将查询参数调整为 Long 后，查询恢复预期的等值匹配行为。

## 2. 问题背景

DMS 有编号相关的数据表，其中一个编号组件 ID 在数据库中定义为数值类型，而 Java 对象中对应字段使用 String。

实际查询时，使用 String 参数出现了与预期不同的查询行为；将 Java 参数类型调整为 Long 后，查询表现恢复为预期的等值查询。

这个案例的价值在于：后端查询不只是检查 SQL 文本，还需要检查数据库字段类型、Java 属性类型、ORM/JDBC 参数绑定和最终执行计划是否一致。

## 3. 60 秒面试表达初稿

> 我之前排查过一个编号查询问题。数据库中对应的组件 ID 字段是数值类型，但 Java 对象中把它定义成了 String。使用这个参数查询时，查询行为和预期不一致；后来把 Java 参数类型调整为 Long，查询恢复为预期的等值匹配。
>
> 这个问题让我注意到，SQL 查询排查不能只看 Mapper 里写了什么，还要确认实体字段类型、参数实际绑定类型以及数据库字段类型是否一致。尤其在关注索引性能时，还要进一步看最终 SQL 和 EXPLAIN 执行计划，确认是否发生隐式转换、索引列转换或扫描范围扩大。
>
> 目前我能确认的是类型调整前后的查询行为差异；是否因此导致全表扫描、是否存在索引失效，以及具体性能改善幅度，需要通过当时的 SQL 和执行计划进一步证明。

## 4. 如何把这个问题排查完整

### 第一步：确认数据库列定义

先查看组件 ID 对应字段的真实类型、是否允许 NULL、是否有索引，以及字段数据是否都符合数值格式。

不能只看 Java Entity 的注释或变量名，要看真实数据库 DDL。

### 第二步：确认 Java 与 ORM 参数类型

检查：

- Entity / DTO 中对应属性的类型；
- Mapper 方法参数类型；
- MyBatis 参数映射或 JDBC set 方法实际使用的类型；
- 是否在 SQL 中对参数或列做了 CAST、CONVERT 等转换。

数据库列是数值类型，不代表 ORM 一定会按数值类型绑定参数。

### 第三步：检查最终 SQL 和绑定参数

需要拿到实际执行的 SQL，以及参数值和 JDBC 类型。只看 Mapper XML 或注解 SQL，可能看不到最终参数绑定行为。

### 第四步：使用执行计划验证

对比类型调整前后的执行计划，重点检查：

- 访问方式是索引查找、索引扫描还是全表/顺序扫描；
- 估算行数与实际行数；
- 是否对索引列应用了函数或类型转换；
- 是否发生隐式类型转换；
- 是否存在其他过滤条件、统计信息或数据分布差异。

MySQL 与 PostgreSQL 的类型转换和优化器行为并不完全相同，必须结合实际数据库产品和版本判断。

### 第五步：验证修改结果

在相同数据、相同查询条件下比较：

- 返回结果是否正确；
- 生成 SQL 和绑定参数类型是否符合预期；
- 执行计划是否发生变化；
- 实际耗时和扫描行数是否改善。

没有前后执行计划和耗时数据，不应宣称“解决了全表扫描”或“性能提升了某个百分比”。

## 5. 面试官可能追问什么

### Q1：为什么 Java String 与数据库数值类型不一致会带来问题？

**专业解释：** ORM/JDBC 会将 Java 参数映射为数据库驱动对应的 SQL 类型。字段类型和参数类型不一致时，数据库可能进行隐式转换，或由框架生成不同的绑定行为；具体影响取决于数据库、驱动、SQL 写法和转换发生的位置。

**大白话：** 数据库里存的是数字，程序却按字符串传。数据库要不要帮你转换、怎么转换，会影响查询的执行方式，所以两边类型最好保持一致。

**项目边界：** 本案例确认了类型调整前后的查询行为差异；具体根因需要 SQL、绑定参数和执行计划证实。

### Q2：类型不一致就一定无法使用索引吗？

**答案：** 不一定。不能简单地说只要 String 查数值字段就一定全表扫描。要看数据库类型转换规则、参数绑定方式、是否对索引列做了转换、优化器选择以及数据分布。应通过 EXPLAIN / EXPLAIN ANALYZE 验证。

### Q3：为什么不直接在 SQL 里 CAST？

**答案：** 如果对索引列做函数或类型转换，可能改变索引可用性；如果只转换参数，影响可能不同。需要结合数据库执行计划判断。更稳妥的做法通常是让应用参数类型与列类型一致，而不是先在 SQL 中补转换。

### Q4：你怎么判断查询是否真正变快？

**答案：** 对比相同数据与查询条件下的执行计划、扫描行数、实际耗时和数据库负载。不能只凭“加了索引”或“改了类型”就认定优化成功。
