# Java 后端求职与面试准备工作区

> 建立日期：2026-11-24  
> 当前阶段：第一版结构迁移，内容待用户持续审计  
> 核心目标：把招聘信息、个人真实经历、岗位匹配、技术学习和面试表达连成可复用的准备流程。

## 1. 这个工作区负责什么？

它不是单纯的技术笔记，也不是某一家公司的临时面试文件夹，而是长期维护的个人求职工作区，主要承担五项工作：

1. **收集面试信息**：保存公司、岗位、招聘要求、面试信息和来源。
2. **维护个人经历**：沉淀真实工作经历、项目职责、技术实践和证据。
3. **匹配岗位与简历**：把岗位要求与个人经历逐项对照，针对不同岗位形成独立简历版本。
4. **学习技术知识**：补齐岗位要求和项目追问涉及的技术原理，区分必须掌握、重点理解和了解即可。
5. **训练面试表达**：把项目经历整理成故事，准备问题、回答、追问，并通过面试复盘持续改进。

## 2. 目录结构

~~~text
job-search/
├── inbox/                 # 尚未整理的招聘和面试信息
├── market-research/       # 跨公司、跨岗位的市场调研与来源数据
├── companies/             # 公司、岗位与招聘信息
├── profile/               # 个人经历事实源、主简历和项目素材
├── applications/           # 每家公司、每个岗位的专项准备
├── knowledge/              # 跨公司复用的技术知识
├── interview-assets/       # 项目故事、问题库和回答框架
└── templates/              # 可复用的记录模板
~~~

## 3. 五类核心资料的边界

| 模块 | 核心问题 | 主要产出 |
|---|---|---|
| companies | 企业需要什么？ | 招聘原文、公司资料、面试信息 |
| profile | 我真实做过什么？ | 主简历、项目经历、技术栈和证据 |
| applications | 我与这个岗位匹配多少？ | JD 匹配、定制简历、准备计划、复盘 |
| knowledge | 我是否真正理解这些技术？ | 原理说明、项目映射、问答和验收标准 |
| interview-assets | 我能否把经历和知识讲清楚？ | 项目故事、问题库、回答框架 |

## 4. 推荐工作流程

1. 零散新看到的招聘信息先放入 inbox，记录来源和日期；跨公司批量调研放入 market-research。
2. 整理后将值得跟进的公司和岗位归入 companies，保留岗位原文和明确的招聘信息。
3. 以 profile 作为个人经历的唯一事实来源，不因某个岗位而改写真实事实。
4. 在 applications 中建立该公司/岗位目录，完成 JD 匹配和简历调整。
5. 将暴露出的知识差距转化为 knowledge 中的学习任务。
6. 将真实项目经历沉淀为 interview-assets 中可复用的项目故事。
7. 面试后记录问题、追问、回答缺口和下一步行动，并回写知识库。

## 5. 知识优先级与掌握状态

优先级用于决定先学什么：

| 等级 | 含义 |
|---|---|
| P0 必须掌握 | 岗位核心要求或真实项目关键技术，必须能解释原理、讲清项目实现并应对追问 |
| P1 重点理解 | 岗位明确涉及或与项目相关，需要理解问题、机制、适用条件和主要风险 |
| P2 了解即可 | 当前岗位次要或尚无实践的扩展知识，能说明概念和用途，不包装成项目经验 |

掌握状态用于记录当前程度：

| 状态 | 含义 |
|---|---|
| S0 | 未学习 |
| S1 | 初步理解 |
| S2 | 能够独立讲解核心原理和流程 |
| S3 | 能分析异常、边界、替代方案并应对追问 |
| S4 | 有本人参与的项目证据或可核验实践材料 |

P0/P1/P2 与 S0–S4 是两套不同维度，不能互相替代。初始评估均待用户审计。

## 7. 维护原则

- 公司招聘原文与我们的分析必须分开。
- 个人经历以真实参与范围为准，不把团队工作写成个人独立成果。
- 没有确认的实现细节标记为“待核实”，不要用通用技术方案填补项目事实。
- 通用知识只维护一份，公司专项通过链接引用。
- 每份岗位定制简历都要能追溯到 profile 中的事实素材。
- 不编造量化结果、技术指标、面试题或面试反馈。
